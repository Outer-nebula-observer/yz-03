# 子课题-1 交付：指挥决策图谱检索引擎（command_graph）

> 依据《记忆引擎开发 SDK v1.0.0》（`memory_engine_sdk.md`）交付。
> 包内目录结构已与目标系统一致（`server/...`、`data/...`），**可直接拖放落位**。

---

## 1. 三步接入

1. 按 §2 把两个目录拖到目标位置；
2. 重启智戎服务；
3. 按 §5 验证（契约自检 + 引擎列表 + 冒烟检索）。

无需修改服务端任何代码：目录名 = 引擎 `name` = `command_graph`，
`__init__.py` 已导出模块级 `engine_plugin`，`discover_plugins()` 会自动注册。

## 2. 包内结构与落位对照

| 本包内路径 | 目标系统路径 | 说明 |
|---|---|---|
| `server/engines/command_graph/` | `server/engines/command_graph/` | 引擎实现（`__init__.py` / `engine.py` / `README.md`） |
| `data/检索数据/知识图谱数据/TIAOLING_CN/` | `data/检索数据/知识图谱数据/TIAOLING_CN/` | 条令库图谱（GraphRAG 索引产物） |
| `data/检索数据/知识图谱数据/ZUOZHAN_CN/` | `data/检索数据/知识图谱数据/ZUOZHAN_CN/` | 案例库图谱（7 篇作战案例） |

每个图谱目录的布局与系统构建层 `build_kg` 的输入口径一致：

```
<KG名>/output/entities.parquet          实体（同时提供 create_final_entities.parquet 兼容副本）
       output/relationships.parquet     关系
       output/communities.parquet       社区
       output/community_reports.parquet 社区报告（Global Search 用）
       output/text_units.parquet        文本单元（逐跳依据用）
       output/documents.parquet         文档
       meta/*.json                      索引元信息
```

## 5. 验证（三条，按顺序）

```bash
# ① 契约自检（离线，无需服务端）——期望 [OK] 契约自检通过，退出码 0
python scripts/validate_engine.py command_graph

# ② 引擎是否注册（需服务端已启动）——期望列表里出现 "name": "command_graph"
curl http://127.0.0.1:8000/api/v2/memory-engine/engines

# ③ HTTP 冒烟——期望 “引擎已注册 ... available=true” 且检索返回若干条
python scripts/smoke_test_engine.py command_graph
```

我们这边的原始自检输出见 `自检结果.txt`；逐项对照见 `契约自检清单（已勾选）.md`。

> **注意（官方冒烟脚本的固定查询词）**：`smoke_test_engine.py` 内部固定用 `"测试查询"` 去检索。
> 本引擎以**图谱实体**为种子，这个词命中不到任何实体时会正常返回 0 条（脚本本身仍返回退出码 0）。
> 所以请在冒烟之后再补一条**带实体名的真实问题**验证，例如：
>
> ```bash
> curl -X POST http://127.0.0.1:8000/api/v2/memory-engine/search \
>   -H "Content-Type: application/json" \
>   -d '{"query":"红方都有哪些导弹？最大射程是多少？","engines":["command_graph"],"top_k":5}'
> ```
>
> 期望：返回 5 条，`score` 0.5~0.96，`source_file` 形如 `知识图谱数据/TIAOLING_CN`。
> 包内 `自检结果.txt` 已列 5 条实测题与返回条数，可直接复用。

## 6. 检索结果字段（对接口径）

| 字段 | 我们的取值 |
|---|---|
| `content` | 实体描述 + 来源文档 + 推理路径 + 逐跳依据（多行文本） |
| `score` | 0~1（已归一化；实测区间约 0.50~0.96） |
| `source_file` | `知识图谱数据/TIAOLING_CN` 或 `知识图谱数据/ZUOZHAN_CN`（检索数据根相对路径、正斜杠） |
| `chunk_id` | `<KG名>:<实体名>`，如 `TIAOLING_CN:目标选择` |
| `engine` | `command_graph` |
| `metadata` | 见下（推理路径等，融合时平铺进 `RetrievalResult.metadata`） |

`metadata` 关键字段：

| 字段 | 说明 |
|---|---|
| `reasoning_path` | 有序推理链路，如 `战斧巡航导弹 -[打击]-> 沙伊拉特空军基地 <-[下令打击]- 特朗普` |
| `hops_detail` | 逐跳明细（from / to / 关系 / 依据 text_unit） |
| `evidence` | 逐跳原文依据（doc + text_unit + 文本片段），可核对、可引用 |
| `seed` / `entity` / `entity_type` / `hops` | 命中的种子实体、实体类型、跳数 |
| `kg_source` / `kgs` / `docs` | 结果出自哪个图谱、涉及哪些文档 |
| `cross_kg_hops` / `cross_doc_hops` | 跨库 / 跨文档跳数 |
| `search_mode` | `local`（实体多跳）/ `global`（社区摘要，整体规律类问题）/ `list`（罗列清单类问题收口） |

结果示例（真实输出截断）：

```json
{
  "content": "[武器装备] 战斧巡航导弹：……\n来源文档：CASE2_沙伊拉特打击_2017\n推理路径：战斧巡航导弹 -[打击]-> 沙伊拉特空军基地\n依据（CASE2_沙伊拉特打击_2017）：……",
  "score": 0.895,
  "source_file": "知识图谱数据/ZUOZHAN_CN",
  "chunk_id": "ZUOZHAN_CN:战斧巡航导弹",
  "engine": "command_graph",
  "metadata": {
    "seed": "战斧巡航导弹",
    "hops": 1,
    "cross_doc_hops": 1,
    "reasoning_path": ["战斧巡航导弹 -[打击]-> 沙伊拉特空军基地"],
    "docs": ["CASE2_沙伊拉特打击_2017"]
  }
}
```

## 7. 建议配置（`config.json`）

插件不自报权重（契约规定），只在 `retrieval` 段配置：

```json
{
  "retrieval": {
    "engine_weights": { "command_graph": 0.6 },
    "engine_timeouts": { "command_graph": 10.0 }
  }
}
```

依据：本引擎实测延迟 p50 ≈ 25 ms、均值 ≈ 81 ms、最大 ≈ 673 ms，10 s 超时留有充足余量。

---

## 8. 数据口径与血缘

- 两份 parquet 是我们用 **GraphRAG 3.1.0（微软官方实现）** 离线索引得到的产物：
  `文本单元 → LLM 实体/关系抽取 → Leiden 社区分层 → 社区报告`，与论文 §Indexing 一致；
- `TIAOLING_CN`：条令库（联合出版物条令，提取规则与概念），2190 实体 / 2089 关系；
- `ZUOZHAN_CN`：案例库（7 篇作战案例，含目标选择、弹目匹配、平台与武器运用），251 实体 / 340 关系；
- **入库与否都可用**：
  - 走共享底座：`python scripts/ingest_all.py --scope kg` 把 parquet 导入 Neo4j + Qdrant（图数据线）；
  - 不入库：本引擎直接读检索数据根下的 parquet（`shared` 模式即是如此）；
- 更新数据：替换 `<KG名>/output/*.parquet` 后重启服务即可（引擎带 mtime 缓存，会自动失效重建）；
- `source_file` / `chunk_id` 一律按「检索数据根相对路径 + 正斜杠」口径，不使用系统绝对路径，
  便于融合去重与文件删除对齐。

---

## 9. 能力与边界（避免误用）

- **只检索、不生成**：`supports_generate=False` / `supports_stream=False`，
  服务端 SSE 层会自动补 `engine_done(status="unsupported")`，插件不实现生成；
- **不 ingest / 不 delete**：数据由构建层负责，插件不认领任何后缀（不会与内建引擎抢路由）；
- **不直连 Neo4j / Qdrant**：通用图查询由系统内建 `graph_rag` 承担；本引擎提供的是
  GraphRAG 论文层能力 —— Local Search 多跳关联 + Global Search 社区摘要 + 可解释推理路径；
- **中文问答**：种子实体按中文词元匹配，提问里带图谱内的实体名（如「爱国者导弹」「战斧巡航导弹」）效果最好。

## 10. 质量情况（我们侧实测，供验收参考）

| 指标 | 数值 | 口径 |
|---|---|---|
| 命中率 hit@8 | 1.00 | 12 题测试集，top_k=8 |
| 召回率 recall@8 | 0.972 | 同上 |
| MRR | 0.541 | 同上 |
| nDCG@8 | 0.664 | 同上 |
| 引用召回 citation_recall | 1.00 | 金标文档被引比例 |
| 逐跳可溯源率 | 1.00（139/139 跳） | 每跳都带 doc + text_unit 依据 |
| 跨文档命中率 | 0.75 | 需要跨文档才能答对的题 |
| 跨库（条令↔案例）命中率 | 0.667 | 需要跨图谱的题 |
| 检索延迟 | p50 25 ms / 均值 81 ms / 最大 673 ms | 单机、无 GPU |

### 10.1 资源占用（实测，单进程）

| 项 | 实测值 | 说明 |
|---|---|---|
| 引擎常驻内存 | 约 53 MB | 载入两份图谱后的**增量**（全部实体 / 关系 / 社区报告 / 文本单元） |
| 进程总内存 | 约 133 MB | 其中 pandas 约 65 MB、Python 解释器 15 MB —— 均为系统本就有的常驻开销 |
| 首次加载耗时 | 0.25 s | 读全部 parquet；之后按文件 mtime 缓存，缓存命中约 4 ms |
| 单次检索耗时 | 约 85 ms | 12 题实测 p50 25 ms、最大 673 ms |
| 并发安全 | 已加固并验证 | 90 次「整体规律类 + 单实体类」混合并发检索，结果与串行完全一致（0 次偏差） |
| 磁盘占用 | 5.4 MB（压缩包） | 图谱 parquet 解压后 7.2 MB |

结论：数据量与内存占用都很小，**接入无需为容量做任何额外准备**；
引擎不常驻线程/连接，随服务端生命周期存在。

## 11. 排障

| 现象 | 原因 | 处理 |
|---|---|---|
| `engines` 列表中本引擎 `available=false` | 没找到图谱数据根 | 确认 `data/检索数据/知识图谱数据/<KG名>/output/*.parquet` 存在；或用环境变量 `COMMAND_GRAPH_KG_ROOT` 指定数据根 |
| 检索 0 条且日志有 WARNING | 同上（日志会打印实际查找路径） | 按日志路径核对落位 |
| 引擎没出现在列表里 | 目录名/导入有问题 | 确认目录名 `command_graph`（不以 `_` 开头、不命中保留名）、`__init__.py` 导出 `engine_plugin`、`pandas`/`pyarrow` 已安装 |
| 检索 0 条但 `available=true` | 问题里没有能命中图谱实体的词 | 改用图谱内实体名提问（如「爱国者导弹」「战斧巡航导弹」「联合目标选择周期」） |
| 官方冒烟脚本显示"检索返回 0 条" | 它固定用 `"测试查询"` 这个无实体词 | 属正常现象；按 §5 的注意用实体名再验一次 |
| 生成的回答很简略 | 本引擎只给检索证据 | 生成由服务端统一编排（`LLMInterface` + `citation_utils`），`content` 已含可引用依据 |
