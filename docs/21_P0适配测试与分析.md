## 三、分析

### 3.1 这些能力是否解决了 P0 对应问题？

| 问题 | 解决程度 | 说明 |
|---|---|---|
| P1 无“场次结束/复盘文本” | ✅ 已解决 | `hook_evolve` 可在任意时刻触发，不依赖 open session；`hook_append_feedback` 支持分段累积 |
| P3 输入形态不同 | ✅ 已解决（输入侧） | `normalize_task` 完成结构化任务→内部输入；若智戎自带查询则原样通过 |
| P4 反馈不是文本 | ⚠️ 基本解决 | `structured_to_review` 把数值/事件转成带教训/经验线索的文本，但仍是“保底转写”，**复盘质量有限** |
| P5 领域分布差异 | 🟡 工具就绪 | `domain_check` 输出词表覆盖/hit@5/min_score 建议，但**真正重标定需要智戎真实数据** |

### 3.2 边界与局限

1. **`structured_to_review` 是规则启发式**：`partially`（部分达成）不会被标记为教训或经验——它只对明确的 success/fail 生效。对“半成功”场景，建议后续用 LLM 版 `review_builder` 生成更细的复盘。
2. **事件驱动进化的“教训质量”取决于反馈材料**：如果智戎只给 `{result:"fail"}` 而没有事件/指标，转写出的教训是通用模板（“需复盘失败环节”），信息量有限。
3. **幂等靠 θ 向量查重**：T5 验证了完全相同的教训不会重复写；但**语义等价但措辞不同的教训**仍可能被当作新经验写入（这是 θ 阈值的固有取舍）。
4. **没有 session 的独立进化不写入场次历史**：`hook_evolve` 在无 session 时直接调 `evolution.evolve_from_review`，不经过 `STATE.sessions`（WebUI 场次历史）；它适用于平台后台自动进化，若需要审计可看进化报告的 `session_id="auto-..."` 与 `forgotten_log`。
5. **domain_check 的 min_score 建议只是“负例上限+0.02”**：是快速启发式；正式接入仍应按 `eval/ablation.py` 的 E 噪声研究协议，用正例/负例分布扫描确定。

### 3.3 对“流水线场次 vs 真实场景”的结论

- **流水线范式没有被破坏**：`ZhirongEventAdapter` 继承原三挂接点，原有 `hook_plan/feedback/close` 行为不变（T4 验证）；
- **新增的事件驱动路径补上了“无结束信号”的场景**：平台可以随时 `append_feedback` + `evolve`，记忆仍然沉淀；
- **结构化反馈转写使 AFSIM 数值结果也能进化**：为智戎“没有复盘文本”的最坏情况提供保底；
- **任务规范化降低了接入成本**：智戎侧只需传 JSON 任务，无需手写 goal/constraints/queries。

### 3.4 后续建议（按优先级）

1. **拿到智戎真实数据后**：
   - 用 `domain_check.py --samples real_samples.json --fact-db ... --exp-db ...` 巡检；
   - 按建议更新 `min_score`，再跑 `eval.ablation` 重标定 θ。
2. **把复盘转写从规则升级为 LLM**：在 `structured_to_review` 里支持 `review_builder=llm`，对结构化指标/事件生成更细复盘（成本增加但质量更好）。
3. **把无 session 的独立进化也接入 WebUI 场次历史**（若想要统一审计）：在 `hook_evolve` 无 session 分支补写一条 `sessions` 记录。
4. **S2 阶段注册表 / S6 scope 分区 / S8 知识锚定**仍按 docs/20 的 P1 计划推进。
