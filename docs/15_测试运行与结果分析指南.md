## 二、逐项测试：怎么跑、看什么、怎么分析

### 2.1 冒烟测试 —— 框架健康检查

```bash
python tests/test_smoke.py
```

**预期输出（尾部）**：
```
全部通过 [OK]
```

**21 个 PASS 对应 14 个测试函数**（覆盖 6 大模块 + 评审修复回归）：

| 函数 | 验证什么 | 如果失败说明 |
|---|---|---|
| test_schema | 遗忘模型/溯源字段 | schema 数据模型或 retention 计算 |
| test_embeddings | Mock 向量确定性/区分度 | embeddings.py |
| test_short_term | 工作记忆 flush/递归摘要/约束不丢 | working_memory.py |
| test_long_term | 双库检索 | factual/experiential store |
| test_retrieval | 混合检索/回填 | hybrid.py |
| test_evolution | 写/合/忘/抽 | memory_evolution.py |
| test_pipeline | 七步闭环 + **真实跨场次复用断言** | pipeline/controller |
| test_boundary | 边界门控/审计 | boundary.py |
| test_bugfix_regressions | 强化落库/单次强化/render | store/hybrid/render |
| test_fix_regressions | 遗忘单位/BM25 缓存/LIKE 转义 | 相关模块 |
| test_integration_zhirong | 三挂接点 mock + 时延 + 降级 | zhirong_adapter.py |
| test_stage_aware | MDMP 模板/亲和/归因/幂等 | stages/hybrid/evolution |
| test_review_fixes | 评审修复回归 9 项（上下文注入/单路/句级抽取/抽象无残留/持久化等） | 各模块 |

**分析口诀**：一行 PASS 对应一个模块——哪一行挂了就先去那个文件；全部 PASS 说明"框架健康"，但它只证明结构正确，**不证明效果**（效果看消融与真模型验证）。

### 2.2 消融 v2 —— 实验证据（重点）

```bash
python -m eval.ablation            # 全量
python -m eval.ablation --quick    # 只需主线时
```

**输出分节解读与判据**：

| 节 | 怎么读 | 关键判据 |
|---|---|---|
| **G0/G1 任务层** | `memory_citation=0`（无装载） | 应为 0；若 >0 说明检索旁路未生效 |
| **G2 仅事实库** | 分类别 `C=0 D=0 G=0`（经验类全 miss） | **应**为 0（这是"空经验库注入"的正确语义，不是 bug） |
| **G3 双库主配置** | `hit@5≈0.64`、分类别 `C=0.63 D=1.0 G=1.0` | 应显著 > **随机基线 0.357**；若 ≈0.36 说明检索失效 |
| **G3 vs G2 显著性** | `Δhit@5≈+0.30, p(置换)=0.0001` | p<0.05 = 双库贡献显著；若 p>0.05 检查用例集是否固定 |
| **G4 跨场次** | 处理组 `hit@5=0.83`，对照组（无场次1）=0 | 对照组必须 0；处理组 >0（5/6 场成功即 0.83） |
| **G5 检索策略** | Mock 下 `hybrid≈0.86 < vector≈0.93`，`干扰压制 hybrid=1.0` | **Mock 下混合不优于单路是预期负结果**；勿当 bug；真模型重跑才是裁决 |
| **G6 阶段亲和** | `on: 干扰压制=1.0 / off: 0.0` | 只要 on>off 即机制生效；p 值受 n=4 限制，方向证据即可 |
| **随机基线** | 单 gold hit@5=0.357（n=14） | 所有 hit@5 的"地板"，任何结论都要对照它 |
| **E 噪声研究** | `min_score=0.16 → 负例返回率=0` | 若 >5%：min_score 需重标定（见 §三问题表） |
| **F 遗忘研究** | 未保护删 10/保护删 0/新写入删 0；检索影响 0/5/5 | 任何"保护被删/新写入被删"= 遗忘模型 bug |
| **C 压缩研究** | truncate 压缩率≈0、summarize≈0.90；约束保留 True | 约束必须始终保留 |
| **S 敏感性** | θ=0.6 拦截 1.0/0.0；stage_bonus>0 干扰压制=1 | Mock 下 θ=0.6 优于默认 0.8（**待决策项**，见 docs/12） |

**数字稳定性**：Mock 是完全确定性的——同一环境重复跑，数字应**完全一致**。若两次不一致，说明有隐藏随机源（如 uuid 进入指标、未固定 seed），需排查（`eval/stats.py` 的 seed 已固定）。

**分析三个"必须警惕"的信号**：
1. G3 hit@5 逼近随机基线 0.357 → 检索大概率失效（检查 min_score 是否过高、种子库是否太薄、embedding 是否没生效）；
2. G4 对照组 >0 → 跨场次 gold 解析混入了种子记忆（检查 `resolve_cross_session_gold` 的 `source.startswith("复盘:")` 过滤）；
3. G2 的 C/D/G >0 → 空经验库注入失败（检查 `build_stores(with_exps=False)` 是否真的没加经验种子）。

### 2.3 GLM 真模型验证 —— 效果证据

```bash
python -m eval.verify_llm                    # 默认模型（.env 的 GLM_MODEL）
python -m eval.verify_llm --model glm-4.5    # 指定旗舰
python -m eval.verify_llm --no-embed         # 跳过 T7（节省额度）
```

**前置**：仓库根 `.env` 已配置 `GLM_API_KEY`（未配置会直接报"缺少 GLM_API_KEY"）。

**23 项检查按 T1–T7 分组 + 判据**：

| 组 | 测什么 | 关键判据 |
|---|---|---|
| T1 连通性与延迟 | 3 次对话 | 全部成功；avg 参考 1–3s（glm-4.5-air）；glm-4.5-flash 20s+ 属限速现象 |
| T2 抽取对比 | Mock vs GLM | GLM 非空、importance 有区分度、无 2.0 滥用、无标记残留 |
| T3 抽象 | 多条经验→通用教训 | 无指令残留、含源内容要点 |
| T4 摘要 | 长文本摘要 | 长度 ≤300 字且非复读 |
| T5 进化端到端 | GLM 抽取×检索闭环 | write≥1；经验库无指令/JSON 残留 |
| **T6 规划任务层** | **GLM 是否真的用记忆写规划** | 宽松引用率 >0（参考 1.00）；约束满足 ≥0.5 |
| T7 embedding | 语义判别力 | 分离度 Δ>0.3（参考 0.63） |

**LLM 非确定性**：两次运行的数字（抽取条数 2/3、约束满足 0.50/1.00）可能不同——这是 LLM 采样导致的**正常波动**。PASS/FAIL 判定基于范围而非精确值；做正式结论时对关键指标跑 ≥3 次取均值±std（`eval/stats.py` 支持）。

**失败排查**：
- 全部失败且报 `3 次失败` → 网络/密钥问题（检查 `.env`）；
- 偶发失败但重试成功 → GLM 偶发 SSL 瞬断，已内置重试，可重跑；
- T2 无 2.0 但 importance 全文 → 需检查 prompt 是否被后续版本改动。

### 2.4 两场次演示 —— "越用越强"的最小可验证闭环

```bash
python examples/demo_pipeline.py
```

**怎么读输出**：
- P001：⑦ 进化报告应 `write: 2`、`abstract: 1`（句子级抽取 + 抽象触发）；
- **关键判定**：P002 的"③ 检索命中"里**必须出现** `source='复盘:P001'` 的条目（并带"电子压制/预备队"内容），且 3 号高地地形排在高地类首位——这才算"记忆真的跨场次复用了"。

如果 P002 没有 `复盘:P001` 条目，按优先级排查：检索阈值过高（min_score）→ 查询词与教训语义差太远 → 进化未写入（看 P001 的 write 计数）。

## 三、结果归档与对比

### 3.1 结果文件

| 文件 | 内容 |
|---|---|
| `eval/results/ablation_report.json` | 全量消融：G0–G6 指标、显著性 p、随机基线、E/F/C/S 专项研究、`_meta`（测试集/embedding/耗时/诚实边界） |
| `eval/results/llm_verification.json` | GLM 验证 23 项：T1–T7 各项 + 原始输出片段 + 环境信息 |

**怎么查看**：
```bash
python -c "import json; d=json.load(open('eval/results/ablation_report.json', encoding='utf-8')); print(json.dumps(d['groups']['G3'], ensure_ascii=False, indent=2))"
```

### 3.2 常用对比场景

| 想回答的问题 | 做法 |
|---|---|
| 双库到底有没有用？ | 看 `G3_vs_G2.p_perm`（Mock 实测 0.0001）；真模型重跑后重新看 |
| 真 embedding 是否带来提升？ | 同一台机器分别用 Mock / GLM embedding 跑 ablation，对比 G3 hit@5 与 C 类分类别 |
| min_score 该取多少？ | 看 E 噪声研究的"负例返回率 vs 正例 hit@5"曲线，取零噪声点（当前 0.16；GLM 探针建议 0.18–0.20） |
| θ 该取多少？ | 看 S 敏感性：近重复拦截率要高、误拦率要为 0（Mock 下 0.6 最均衡） |
| GLM 模型该选哪个？ | 对同一任务跑 `verify_llm --model X`，对比 T2 抽取条数/T5 写入/T6 引用率与延迟 |
| 消融数字是否可复现？ | Mock 应逐位一致；GLM 跑 3 次看波动范围 |

### 3.3 报告引用规范（写论文/答辩时）

- 引用消融数字时**必须同时给随机基线**（如："双库 hit@5=0.636，随机基线 0.357，配对置换 p=0.0001"）；
- 引用真模型数字时**注明模型与一次运行 vs 多次均值**（如："glm-4.5-air ×3 次，宽松引用率 1.00（三次均如此）"）；
- 诚实边界：Mock 下"结构正确性"证据、真模型下"效果"证据——不要混用。

## 四、常见问题与排查

| 现象 | 可能原因 | 解决 |
|---|---|---|
| 控制台中文乱码 | Windows 默认 GBK | `chcp 65001` 后再运行 |
| 冒烟某一 PASS 消失 | 该模块回归 | 看函数名定位模块；绝大多数情况是改了数据模型没同步 |
| 消融数字与本文不符 | 运行环境/版本不同 | Mock 应逐位一致；若不一致先 `git log` 确认代码版本 |
| G3 接近随机基线 | min_score 过高或 embedding 未生效 | 跑 E 噪声研究检查；确认 `MemoryController(embedding=真模型)` 真的注入了 |
| verify_llm 全部失败 | .env 缺失/密钥错/网络断 | `cat ../../.env`，临时 `curl` 测 bigmodel.cn；已内置重试 |
| verify_llm 偶发单组失败 | GLM 偶发瞬断/限流 | 直接重跑（重试已在代码层）；多次失败再查网络 |
| WebUI 自测失败 1 项 | 服务未启动或端口占用 | 先确认 `/api/status` 可访问；`pkill -f webui/server.py` 后重启 |
| E 噪声负例返回率升高 | min_score 标定失效（换 embedding 后） | 按 E/S 协议重标定（docs/13 §1.2） |
| 演示 P002 无"复盘:P001" | 进化未写 / 阈值过高 / 查询不匹配 | 看 P001 write 数；临时把 min_score 调低验证链路；再调查询 |
