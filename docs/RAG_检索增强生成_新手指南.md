## 1. 什么是RAG？

### 1.1 基本定义
**检索增强生成（Retrieval-Augmented Generation，RAG）** 是一种结合了信息检索和文本生成的人工智能技术。它通过从外部知识库中检索相关信息，然后利用这些信息来增强大型语言模型（LLM）的生成能力。

### 1.2 简单类比
想象一下你在参加考试：
- **传统LLM**：就像你只凭记忆答题，可能会忘记或记错
- **RAG**：就像允许你翻书查找资料，然后基于书本内容组织答案

### 1.3 核心思想
RAG的核心思想是：**"先检索，后生成"**。它不依赖模型记忆所有知识，而是在需要时动态获取相关信息。

## 2. 为什么需要RAG？

### 2.1 解决LLM的局限性

| 问题 | 描述 | RAG的解决方案 |
|------|------|---------------|
| **知识截止** | 模型训练数据有时间限制 | 实时检索最新信息 |
| **幻觉问题** | 模型可能生成不准确的内容 | 基于检索到的真实信息生成 |
| **专业领域知识不足** | 通用模型缺乏特定领域深度知识 | 检索专业文档和数据库 |
| **无法访问私有数据** | 模型没有训练过私有数据 | 连接企业内部知识库 |

### 2.2 RAG的优势
1. **减少幻觉**：基于检索到的事实生成内容
2. **知识可更新**：无需重新训练模型，只需更新知识库
3. **可追溯性**：可以提供信息来源，增强可信度
4. **成本效益**：相比微调模型，RAG实现成本更低

## 3. RAG的核心组件

### 3.1 基础架构图
```
用户查询 → 检索器 → 知识库 → 相关文档 → 生成器 → 最终答案
```

### 3.2 三大核心组件

#### 3.2.1 文档处理器（Document Processor）
- **功能**：将原始文档转换为可检索的格式
- **关键步骤**：
  - 文档解析（PDF、Word、网页等）
  - 文本分块（Chunking）
  - 向量化（Embedding）
  - 索引构建

#### 3.2.2 检索器（Retriever）
- **功能**：根据用户查询找到最相关的文档片段
- **常见方法**：
  - 向量相似度搜索
  - 关键词搜索（BM25）
  - 混合搜索

#### 3.2.3 生成器（Generator）
- **功能**：基于检索到的文档生成最终答案
- **工作方式**：
  - 将检索结果与原始查询组合
  - 使用LLM生成连贯、准确的回答

## 4. 经典RAG架构

### 4.1 工作流程
```
1. 索引阶段（离线）：
   文档 → 分块 → 向量化 → 存入向量数据库

2. 查询阶段（在线）：
   用户问题 → 向量化 → 向量搜索 → 获取相关文档 → LLM生成答案
```

### 4.2 文档分块策略
- **固定大小分块**：按字符数或词数分割
- **语义分块**：按段落、章节或语义边界分割
- **递归分块**：先按大结构分割，再细分子块

### 4.3 向量化技术
- **稠密向量**：使用深度学习模型（如BERT、OpenAI Embeddings）
- **稀疏向量**：TF-IDF、BM25等传统方法
- **混合向量**：结合稠密和稀疏向量

### 4.4 向量数据库
常用工具：
- **FAISS**：Facebook的相似度搜索库
- **Pinecone**：云原生向量数据库
- **Milvus**：开源向量数据库
- **Chroma**：轻量级向量数据库
- **Weaviate**：支持混合搜索的向量数据库

## 5. GraphRAG：基于知识图谱的RAG

### 5.1 什么是GraphRAG？
**GraphRAG（Graph-based Retrieval-Augmented Generation）** 是一种将知识图谱（Knowledge Graph）与检索增强生成（RAG）相结合的先进架构。它通过构建和利用实体-关系网络，显著增强了对复杂关系和多跳推理的支持能力。

### 5.2 GraphRAG版本演进概览

| 版本 | 核心特征 | 技术突破 | 适用场景 |
|------|----------|----------|----------|
| **GraphRAG 1.0** | 基础图增强RAG | 静态知识图谱构建 | 简单问答、事实查询 |
| **GraphRAG 2.0** | 社区检测与层次化图 | 图社区摘要、层次化检索 | 复杂推理、领域知识 |
| **GraphRAG 3.0** | 动态图与多模态支持 | 动态图更新、多模态融合 | 实时系统、多模态应用 |

---

### 5.3 GraphRAG 1.0：基础图增强RAG

#### 5.3.1 定义与核心思想
GraphRAG 1.0是第一个将知识图谱与RAG结合的版本，核心思想是**"图结构化检索"**。它将文档转换为结构化的知识图谱，然后利用图结构进行更精确的检索。

#### 5.3.2 核心优势
- **关系感知**：通过实体关系网络理解上下文
- **结构化存储**：知识以图形式存储，保持结构信息
- **基础推理**：支持简单的路径推理
- **可解释性**：可以展示检索到的图路径

#### 5.3.3 具体技术实现
```
技术栈：
1. 实体识别（NER）：使用BERT、spaCy等模型识别实体
2. 关系抽取：基于预训练模型或规则抽取关系
3. 图存储：Neo4j、JanusGraph等图数据库
4. 图检索：基于图遍历的子图检索
5. 答案生成：将图结构转换为文本描述后输入LLM
```

#### 5.3.4 工作流程
```
文档处理流程：
原始文档 → 句子分割 → 实体识别 → 关系抽取 → 三元组构建 → 知识图谱构建

查询处理流程：
用户问题 → 实体识别 → 图子图检索 → 路径排序 → 答案生成
```

#### 5.3.5 局限性
- **静态图**：构建后难以更新
- **规模限制**：大规模图效率低
- **查询复杂度**：复杂查询需要多跳推理

### 5.4 GraphRAG 2.0：社区检测与层次化图

#### 5.4.1 定义与核心思想
GraphRAG 2.0引入了**图社区检测**和**层次化图结构**，核心思想是**"分而治之"**。它将大型知识图谱划分为多个社区，每个社区代表一个主题或领域，实现更高效的检索和推理。

#### 5.4.2 核心优势
- **层次化组织**：知识按社区层次组织，支持宏观和微观检索
- **社区摘要**：为每个社区生成摘要，提高检索效率
- **规模扩展**：支持大规模知识图谱
- **复杂推理**：支持跨社区的复杂推理

#### 5.4.3 具体技术实现
```
关键技术：
1. 图社区检测：Louvain、Label Propagation等算法
2. 社区摘要生成：使用LLM为每个社区生成摘要
3. 层次化索引：构建多级图索引
4. 混合检索：结合图遍历和向量搜索
5. 社区路由：根据查询选择相关社区
```

#### 5.4.4 层次化图结构
```
Level 0: 原始实体-关系图
Level 1: 社区级图（每个社区是一个节点）
Level 2: 领域级图（多个社区组成领域）
Level 3: 全局图（所有领域）
```

#### 5.4.5 社区检索算法
```python
# 伪代码：社区检索
def community_retrieval(query, graph):
    # 1. 识别查询中的实体
    entities = extract_entities(query)
    
    # 2. 在图中定位实体所在的社区
    communities = find_communities(entities, graph)
    
    # 3. 对社区进行排序
    ranked_communities = rank_communities(communities, query)
    
    # 4. 从相关社区中检索信息
    results = retrieve_from_communities(ranked_communities, query)
    
    return results
```

### 5.7 GraphRAG核心技术深入解析

#### 5.7.1 知识图谱构建技术
```python
# 知识图谱构建流程
class KnowledgeGraphBuilder:
    def __init__(self):
        self.ner_model = load_ner_model()      # 实体识别模型
        self.re_model = load_re_model()        # 关系抽取模型
        self.graph_db = connect_graph_db()     # 图数据库连接
    
    def build_graph(self, documents):
        for doc in documents:
            # 1. 句子分割
            sentences = split_sentences(doc)
            
            for sent in sentences:
                # 2. 实体识别
                entities = self.ner_model.predict(sent)
                
                # 3. 关系抽取
                relations = self.re_model.predict(sent, entities)
                
                # 4. 三元组构建
                triples = build_triples(entities, relations)
                
                # 5. 存入图数据库
                self.graph_db.insert_triples(triples)
        
        return self.graph_db
```

#### 5.7.2 图检索算法
```python
# 图检索算法
class GraphRetriever:
    def __init__(self, graph_db):
        self.graph = graph_db
    
    def retrieve(self, query, max_hops=2):
        # 1. 查询理解
        query_entities = self.parse_query(query)
        
        # 2. 多跳检索
        results = []
        current_entities = query_entities
        
        for hop in range(max_hops):
            # 查找相邻节点
            neighbors = self.get_neighbors(current_entities)
            
            # 边关系过滤
            filtered = self.filter_by_relations(neighbors, query)
            
            results.extend(filtered)
            current_entities = [n['entity'] for n in neighbors]
        
        # 3. 结果排序
        ranked_results = self.rank_results(results, query)
        
        return ranked_results
```

#### 5.7.3 社区检测算法
```python
# Louvain社区检测算法
import community as community_louvain
import networkx as nx

def detect_communities(graph):
    # 转换为NetworkX图
    G = nx.Graph()
    for node in graph.nodes():
        G.add_node(node)
    for edge in graph.edges():
        G.add_edge(edge['source'], edge['target'], weight=edge['weight'])
    
    # 应用Louvain算法
    partition = community_louvain.best_partition(G)
    
    # 按社区组织节点
    communities = {}
    for node, comm_id in partition.items():
        if comm_id not in communities:
            communities[comm_id] = []
        communities[comm_id].append(node)
    
    return communities
```

## 6. 多模态RAG：统一记忆与检索

> **🎯 子课题核心问题**：多模态知识统一记忆与检索 —— 解决"只认字、不识表不识图"的根本挑战

### 6.1 为什么需要多模态RAG？——从"只认字"到"识表识图"

#### 6.1.1 传统RAG的根本局限

传统RAG系统本质上是一个**纯文本管道**：

```
传统RAG的信息流动：
┌─────────────┐     ┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│  多模态文档  │ ──→ │  文本提取    │ ──→ │  纯文本检索  │ ──→ │  文本生成    │
│  (含图表)    │     │  (丢失视觉)  │     │  (无跨模态)  │     │  (无图理解)  │
└─────────────┘     └─────────────┘     └─────────────┘     └─────────────┘
         ▲                                                            │
         └──────────── 大量视觉语义信息在此丢失 ────────────────────────┘
```

这种架构存在一个**致命的信息瓶颈**：

| 信息类型 | 在传统RAG中的处理 | 信息损失 | 影响 |
|----------|-------------------|----------|------|
| **纯文本** | ✅ 完整保留 | 无 | 正常工作 |
| **表格数据** | ⚠️ OCR转文本 | 结构关系丢失 | 数据含义扭曲 |
| **统计图表** | ❌ 通常丢弃或仅提取标题 | 100%视觉信息 | 趋势/对比完全丢失 |
| **流程图/架构图** | ❌ 通常丢弃 | 100%结构信息 | 关系/逻辑完全丢失 |
| **公式** | ⚠️ OCR转文本 | 数学语义丢失 | 推理链断裂 |
| **图像中的文字** | ⚠️ OCR提取 | 空间布局丢失 | 上下文关联断裂 |

#### 6.1.2 现实世界的多模态需求

让我们看一个具体的例子。假设用户有一个技术文档，其中包含：

```
📄 技术文档的典型内容构成：

[文本段落] "我们的系统在A数据集上取得了显著改进..."
    ↓ 用户读到文字，能理解

[表格] 
┌──────────┬──────────┬──────────┐
│ 方法     │ 准确率   │ 推理速度 │
├──────────┼──────────┼──────────┤
│ 我们的方法│ 95.2%   │ 120ms   │
│ 基准方法  │ 87.3%   │ 180ms   │
└──────────┴──────────┴──────────┘
    ↓ 传统RAG：OCR可能读成一串混乱文本
    ↓ 多模态RAG：理解行列关系、数值对比

[折线图] 显示不同epoch下模型准确率的变化趋势
    ↓ 传统RAG：完全丢失（仅保留标题"图3：训练曲线"）
    ↓ 多模态RAG：理解趋势走向、拐点、收敛性

[架构图] 系统整体设计，包含5个模块及其数据流
    ↓ 传统RAG：完全丢失
    ↓ 多模态RAG：理解模块间依赖关系
```

**传统RAG对这个文档的回答**：
> "我们的方法准确率95.2%，推理速度120ms。" （只能回答文本部分能覆盖的问题）

**多模态RAG对这个文档的回答**：
> "我们的方法在准确率（95.2% vs 87.3%）和推理速度（120ms vs 180ms）上均优于基准方法。从训练曲线看，模型在约20个epoch后趋于收敛，最终稳定在95%左右。系统架构包含5个核心模块……" （综合文本、表格、图表、架构图的完整理解）

#### 6.1.3 多模态RAG的定义

**多模态RAG（Multimodal RAG）** 是传统RAG的扩展范式，它能够：
- **统一处理**文本、图像、表格、公式、音频、视频等多种模态数据
- **跨模态检索**：用文本查询检索相关图像，用图像查询检索相关文本
- **模态无关的记忆**：将不同模态的知识映射到统一的表示空间
- **多模态生成**：基于检索到的多模态证据生成回答

### 6.2 多模态记忆系统：核心架构与设计原则

#### 6.2.1 什么是"多模态记忆系统"？

将AI系统类比为人脑：

```
人脑记忆系统 vs 多模态AI记忆系统：

人脑：
┌─────────────────────────────────────────────────┐
│  感觉记忆（视觉/听觉/触觉）                       │
│    ↓ 注意力筛选                                   │
│  短时工作记忆（多感官整合）                        │
│    ↓ 编码巩固                                     │
│  长时记忆（语义记忆 + 情景记忆）                   │
│    → 跨模态关联：看到苹果 → 想起红色、甜味、脆响   │
└─────────────────────────────────────────────────┘

多模态AI记忆系统：
┌─────────────────────────────────────────────────┐
│  多模态输入（文本/图像/表格/音频）                 │
│    ↓ 模态编码器                                   │
│  统一嵌入空间（模态无关表示）                      │
│    ↓ 知识图谱构建                                 │
│  多模态记忆库（结构化 + 向量化存储）               │
│    → 跨模态检索：文本查询 → 同时返回相关图像+表格  │
└─────────────────────────────────────────────────┘
```

**核心问题：多模态知识统一记忆与检索**

这包含三个层次的统一：

| 统一层次 | 含义 | 技术挑战 |
|----------|------|----------|
| **表示统一** | 不同模态数据映射到同一向量空间 | 跨模态对齐（Cross-modal Alignment） |
| **索引统一** | 文本/图像/表格使用统一的索引机制 | 多模态索引结构设计 |
| **检索统一** | 一次查询同时检索所有相关模态 | 模态无关的排序与融合 |

#### 6.3.2 图表知识的特殊处理

图表（Charts/Diagrams）是多模态知识构建中最具挑战性的部分：

```
图表类型的层次化理解：

Level 1: 低级视觉特征
├── 颜色分布、线条形状、区域分割
└── 技术：CNN/ViT特征提取

Level 2: 中级结构识别
├── 图表类型识别（折线图/柱状图/饼图/散点图）
├── 坐标轴识别、图例识别
├── 数据点/数据系列提取
└── 技术：目标检测 + OCR + 规则引擎

Level 3: 高级语义理解
├── 趋势分析（上升/下降/稳定/周期性）
├── 对比分析（哪组数据更优？差距多大？）
├── 因果推断（A变化是否导致B变化？）
└── 技术：VLM（视觉语言模型）推理
```

**关键技术：视觉语言模型（VLM）在图表理解中的应用**

```python
# 图表理解的核心流程（概念代码）
class ChartUnderstandingPipeline:
    def __init__(self):
        self.chart_detector = load_chart_detector()    # 图表类型检测
        self.data_extractor = load_data_extractor()    # 数据点提取
        self.vlm = load_vision_language_model()        # 视觉语言模型

    def understand_chart(self, chart_image):
        # Step 1: 图表类型识别
        chart_type = self.chart_detector.classify(chart_image)
        # 例如: "line_chart", "bar_chart", "pie_chart"

        # Step 2: 结构化数据提取
        if chart_type == "line_chart":
            data_points = self.data_extractor.extract_line_chart(chart_image)
            # 提取：X轴标签、Y轴标签、各数据系列的点
        elif chart_type == "bar_chart":
            data_points = self.data_extractor.extract_bar_chart(chart_image)
            # 提取：类别名、各类别数值
        elif chart_type == "pie_chart":
            data_points = self.data_extractor.extract_pie_chart(chart_image)
            # 提取：各扇区标签和比例

        # Step 3: 使用VLM生成语义描述
        semantic_description = self.vlm.generate_description(
            image=chart_image,
            prompt=f"详细描述这个{chart_type}的内容，包括趋势、对比和关键发现"
        )

        # Step 4: 生成结构化知识
        structured_knowledge = {
            "type": chart_type,
            "data": data_points,
            "semantic_description": semantic_description,
            "trends": self.analyze_trends(data_points),
            "comparisons": self.analyze_comparisons(data_points)
        }

        return structured_knowledge
```

```python
# 概念代码：多模态知识图谱构建
class MultimodalKnowledgeGraph:
    """多模态知识图谱：统一管理文本、图像、表格、公式知识"""

    def __init__(self):
        self.text_entities = {}      # 文本实体库
        self.image_entities = {}     # 图像实体库
        self.table_entities = {}     # 表格实体库
        self.equation_entities = {}  # 公式实体库
        self.cross_modal_links = []  # 跨模态关系

    def process_document(self, document):
        """端到端文档处理"""

        # Step 1: 多模态内容提取
        content_list = self.extract_multimodal_content(document)
        # content_list = [
        #   {"type": "text", "text": "引言部分...", "page_idx": 0},
        #   {"type": "image", "img_path": "fig1.jpg", "caption": "图1: 架构图", "page_idx": 1},
        #   {"type": "table", "body": "|...|...|", "caption": "表1: 对比", "page_idx": 2},
        #   {"type": "equation", "latex": "E=mc^2", "page_idx": 3},
        # ]

        # Step 2: 各模态独立处理
        for item in content_list:
            if item["type"] == "text":
                entities = self.process_text(item)
            elif item["type"] == "image":
                entities = self.process_image(item)  # 使用VLM
            elif item["type"] == "table":
                entities = self.process_table(item)  # 保持结构
            elif item["type"] == "equation":
                entities = self.process_equation(item)  # 数学语义

        # Step 3: 构建跨模态关系
        # "如图1所示" → 文本实体 ---[references]--> 图像实体
        # "数据如表1" → 文本实体 ---[cites]--> 表格实体
        # "公式(1)描述" → 文本实体 ---[formalizes]--> 公式实体
        self.build_cross_modal_relations(content_list)

        # Step 4: 存入统一索引
        self.index_all_entities()

    def process_image(self, image_item):
        """图像处理：使用VLM生成语义描述"""
        # 1. VLM理解图像内容
        description = self.vlm.describe(image_item["img_path"])
        # "这是一个系统架构图，包含5个模块：...",
        #  "数据流从左到右依次经过..."

        # 2. 识别图像中的视觉实体
        visual_entities = self.vlm.extract_entities(image_item["img_path"])
        # ["模块A", "模块B", "数据库", "API接口"]

        # 3. 生成多层表示
        entity = {
            "id": generate_id(),
            "type": "image",
            "original_path": image_item["img_path"],
            "caption": image_item.get("caption", ""),
            "vlm_description": description,
            "visual_entities": visual_entities,
            "embedding": self.image_encoder.encode(image_item["img_path"]),
            "text_embedding": self.text_encoder.encode(description),
            "page_idx": image_item["page_idx"]
        }

        self.image_entities[entity["id"]] = entity
        return entity

    def process_table(self, table_item):
        """表格处理：保持结构化语义"""
        # 1. 解析表格结构
        parsed = self.table_parser.parse(table_item["body"])

        # 2. 生成语义摘要
        summary = self.llm.summarize_table(parsed)

        # 3. 提取数据关系
        relationships = self.analyze_table_relationships(parsed)
        # 例如：{"row_comparison": "我们的方法 > 基准方法 (both metrics)"}

        entity = {
            "id": generate_id(),
            "type": "table",
            "structure": parsed,          # 保持结构化数据
            "caption": table_item.get("caption", ""),
            "semantic_summary": summary,
            "data_relationships": relationships,
            "embedding": self.text_encoder.encode(
                f"{table_item.get('caption', '')} {summary}"
            ),
            "page_idx": table_item["page_idx"]
        }

        self.table_entities[entity["id"]] = entity
        return entity
```

#### 6.4.4 多模态入库的关键挑战与解决方案

| 挑战 | 问题描述 | 解决方案 |
|------|----------|----------|
| **模态对齐** | 不同模态的特征空间不一致 | 对比学习（Contrastive Learning）对齐嵌入空间 |
| **信息保真** | 模态转换过程中信息损失 | 多层表示：原始数据 + 语义描述 + 向量嵌入 |
| **结构保持** | 表格/图表的结构关系丢失 | 结构化存储 + 关系标注 |
| **跨模态关联** | 不同模态间的语义连接断裂 | 自动关系抽取 + 知识图谱连接 |
| **规模扩展** | 多模态数据量远大于纯文本 | 分层索引 + 模态感知缓存 |

### 6.5 研究内容三：模态无关的记忆索引与检索

#### 6.5.1 模态无关的统一嵌入空间

**核心思想**：将所有模态的数据映射到同一个向量空间，使得语义相似的内容（无论什么模态）在向量空间中距离相近。

```
统一嵌入空间的直觉理解：

向量空间示意（二维投影）：

        ▲ 语义维度
        │
        │   ● "准确率对比表"
        │   ▲ 表格图片
        │
        │       ★ 用户查询："模型准确率比较"
        │
        │           ◆ "准确率提升7.9%"  ◇ 相关文本段落
        │
        └──────────────────────────────────→ 语义维度

三种模态（★查询、●/▲表格、◆/◇文本）在统一空间中聚类
```

**关键技术：跨模态嵌入模型**

```
跨模态嵌入模型的演进：

CLIP (2021)
├── 对比学习：图像-文本配对训练
├── 统一空间：图像和文本共享嵌入维度
├── 局限：仅支持图像-文本，不支持表格/公式
└── 代表应用：以图搜图、以文搜图

ALIGN (2021)
├── Google版本：更大规模噪声数据训练
├── 更强鲁棒性：对噪声配对更宽容
└── 局限：同样仅图像-文本

Florence (2021)
├── 微软版本：多任务学习
├── 统一视觉-语言表示
└── 局限：表格/公式支持有限

ColPali (2024) ⭐
├── 文档级视觉检索
├── 直接对文档页面图像编码
├── 绕过传统OCR流水线
└── 优势：保留视觉布局信息

通用多模态嵌入 (2025) ⭐⭐
├── 文本 + 图像 + 表格 + 公式 统一编码
├── 基于VLM的端到端嵌入
├── 支持任意模态组合查询
└── 前沿方向：真正的模态无关
```

#### 6.5.2 混合检索架构

实际系统通常采用**混合检索**策略，结合多种检索方式的优势：

```
模态无关的混合检索架构：

用户查询
    │
    ├──→ [文本查询分支] ──→ 文本向量检索（稠密）──┐
    │                                              │
    ├──→ [文本查询分支] ──→ 关键词检索（稀疏BM25）─┤
    │                                              ├──→ 融合排序 ──→ 最终结果
    ├──→ [图像查询分支] ──→ 视觉向量检索 ──────────┤
    │                                              │
    └──→ [统一嵌入分支] ──→ 跨模态向量检索 ─────────┘
                                │
                                ▼
                    ┌───────────────────┐
                    │  结果融合与重排序   │
                    │  • 分数归一化      │
                    │  • 模态感知加权    │
                    │  • 上下文一致性    │
                    └───────────────────┘
```

**检索融合算法**：

```python
class ModalityAgnosticRetriever:
    """模态无关的混合检索器"""

    def __init__(self):
        self.text_retriever = TextDenseRetriever()     # 文本稠密检索
        self.sparse_retriever = BM25Retriever()         # BM25稀疏检索
        self.multimodal_retriever = MultimodalRetriever()  # 跨模态检索
        self.reranker = CrossModalReranker()            # 跨模态重排序

    def retrieve(self, query, query_modality="text", top_k=10):
        """
        统一检索接口：支持任意模态查询

        query_modality: "text" | "image" | "table" | "mixed"
        """

        all_candidates = []

        if query_modality == "text":
            # 文本查询：三种检索并行
            dense_results = self.text_retriever.search(query, top_k=top_k*2)
            sparse_results = self.sparse_retriever.search(query, top_k=top_k*2)
            cross_modal_results = self.multimodal_retriever.search(
                query, target_modalities=["text", "image", "table", "equation"],
                top_k=top_k*2
            )

        elif query_modality == "image":
            # 图像查询：直接跨模态检索
            cross_modal_results = self.multimodal_retriever.search(
                query, source_modality="image",
                target_modalities=["text", "table", "image"],
                top_k=top_k*2
            )
            dense_results = []
            sparse_results = []

        # Step 1: 分数归一化（不同检索器的分数尺度不同）
        all_candidates = self.normalize_scores(
            dense_results + sparse_results + cross_modal_results
        )

        # Step 2: 跨模态重排序（考虑模态间语义一致性）
        reranked = self.reranker.rerank(
            query=query,
            candidates=all_candidates,
            query_modality=query_modality
        )

        # Step 3: 多样性保证（避免返回同一模态的重复结果）
        diverse_results = self.ensure_modality_diversity(reranked, top_k)

        return diverse_results[:top_k]

    def normalize_scores(self, candidates):
        """Min-Max归一化，统一不同检索器的分数尺度"""
        if not candidates:
            return []

        scores = [c["score"] for c in candidates]
        min_s, max_s = min(scores), max(scores)
        range_s = max_s - min_s if max_s > min_s else 1

        for c in candidates:
            c["normalized_score"] = (c["score"] - min_s) / range_s

        return candidates
```

除了向量检索，**知识图谱**提供了一种补充的检索路径：

```
图结构检索的优势场景：
```

```
│ • 图像描述通常只是粗粒度的，丢失细节       │

瓶颈2: 检索瓶颈
┌──────────────────────────────────────────┐
│ 问题：所有数据都被压缩为文本               │
```

##### 实现示例

```python
# MRAG 1.0 的典型实现流程（概念代码）
class MRAGv1:
    """MRAG 1.0: 伪多模态 - 将所有模态转换为文本"""

    def __init__(self):
        self.text_splitter = RecursiveCharacterTextSplitter()
        self.image_captioner = load_blip2()        # 图像描述模型
        self.table_parser = load_tablenet()         # 表格解析模型
        self.embedder = OpenAIEmbeddings()          # 文本嵌入
        self.vectorstore = FAISS(...)               # 向量数据库
        self.llm = ChatOpenAI(model="gpt-4")       # 纯文本LLM

    def index_document(self, document):
        """文档解析与索引"""
        # Step 1: 解析文档，提取所有内容
        elements = parse_document(document)
        # elements = [
        #   {"type": "text", "content": "我们的方法在..."},
        #   {"type": "image", "content": <PIL.Image>},
        #   {"type": "table", "content": [["方法","准确率"],...]},
        # ]

        chunks = []
        for elem in elements:
            if elem["type"] == "text":
                # 文本直接分块
                chunks.extend(self.text_splitter.split(elem["content"]))

            elif elem["type"] == "image":
                # ❌ 关键操作：图像 → 文本描述
                caption = self.image_captioner.generate(elem["content"])
                # "一张显示模型准确率对比的折线图，蓝色线代表..."
                chunks.append(caption)

            elif elem["type"] == "table":
                # ❌ 关键操作：表格 → 文本序列
                table_text = self.table_parser.to_markdown(elem["content"])
                # "| 方法 | 准确率 |\n|---|---|\n| 我们 | 95.2% |"
                chunks.append(table_text)

        # Step 2: 全部作为文本嵌入和索引
        embeddings = self.embedder.embed_documents(chunks)
        self.vectorstore.add(embeddings, chunks)

    def query(self, user_query):
        """查询（与传统RAG完全相同）"""
        # 仅支持文本查询
        results = self.vectorstore.search(user_query, top_k=5)
        # results 只包含文本块和图像描述
        prompt = f"基于以下信息回答：\n{results}\n\n问题：{user_query}"
        return self.llm.generate(prompt)
```

#### 6.6.3 MRAG 2.0：真多模态（True Multimodal）

##### 核心思想

MRAG 2.0标志着进入**"真多模态"时代**。与MRAG 1.0最大的不同是：**不再将多模态数据转换为文本，而是保留原始多模态数据**，利用多模态大语言模型（MLLM）直接处理原始图像、表格等。

```
MRAG 2.0 的核心逻辑：
多模态文档 → [MLLM统一描述] → 保留原始数据 + 文本描述
                    │
                    ├── 原始图像 → 存入多模态向量库
                    ├── 文本描述 → 存入文本向量库
                    └── 跨模态检索 → 文本查询可检索图像
                    │
                    ▼
        MLLM直接处理原始多模态数据 → 多模态回答
```

##### 技术架构

```
MRAG 2.0 架构图：

┌─────────────────────────────────────────────────────────┐
│                  文档解析与索引（Document Parsing）        │
│                                                         │

│          ┌───────────┴───────────┐                       │
│          ▼                       ▼                       │

│                                                         │
│  用户查询（文本/图像）                                     │

│      │                                                  │

└─────────────────────────────────────────────────────────┘
```

##### 核心技术组件

```
MRAG 2.0 的关键技术突破：

1. MLLM统一描述（替代多模型方案）
   ├── 优势：
   │   • 单一模型处理所有模态，简化系统架构
   │   • 利用MLLM的强大表示能力
   │   • 跨模态一致性更好
   ├── 代表模型：
   │   • GPT-4V/GPT-4o（OpenAI）
   │   • Qwen-VL / Qwen2-VL（阿里）
   │   • InternVL（上海AI Lab）
   │   • LLaVA系列
   └── 应用：
       • 图像描述生成（Image Captioning）
       • 表格语义摘要
       • 图表内容理解

2. 跨模态检索（Cross-Modal Retrieval）
   ├── 核心技术：
   │   • CLIP（Contrastive Language-Image Pre-training）
   │   • ALIGN（Google多模态嵌入）
   │   • ColPali（文档级视觉检索）
   ├── 工作原理：
   │   • 图像和文本共享同一嵌入空间
   │   • 文本查询可以直接计算与图像的相似度
   │   • 实现"以文搜图"和"以图搜文"
   └── 检索策略：
       • 文本查询 → 文本向量库 + 多模态向量库
       • 图像查询 → 多模态向量库
       • 结果融合与重排序

3. 多模态生成（Multimodal Generation）
   ├── 核心能力：
   │   • MLLM直接处理原始图像+文本
   │   • 无需将图像转换为文本描述
   │   • 保留视觉细节和空间信息
   ├── 实现方式：
   │   • 图像编码 → 视觉token → 与文本token联合输入LLM
   │   • 视觉注意力机制处理图像区域
   │   • 生成时可引用图像中的具体区域
   └── 优势：
       • 信息损失远小于MRAG 1.0
       • 对复杂图文混合问题效果显著提升
```

##### 与MRAG 1.0的关键差异

```
MRAG 1.0 vs MRAG 2.0 对比：

文档解析：
  MRAG 1.0: 图像 → BLIP描述 → 文本     ❌ 信息损失大
  MRAG 2.0: 图像 → 保留原始图 + VLM描述  ✅ 保留视觉信息

知识库存储：
  MRAG 1.0: 仅存储文本向量              ❌ 无图像向量
  MRAG 2.0: 文本向量 + 多模态向量        ✅ 双向量库

检索能力：
  MRAG 1.0: 仅文本查询 → 文本结果       ❌ 无跨模态
  MRAG 2.0: 文本查询 → 文本+图像结果     ✅ 跨模态检索
           图像查询 → 相关文本+图像      ✅ 任意模态查询

生成方式：
  MRAG 1.0: LLM处理纯文本输入           ❌ 无视觉理解
  MRAG 2.0: MLLM处理原始图像+文本        ✅ 端到端多模态
```

```
MRAG 2.0 面临的新挑战：

挑战1: 文本查询准确性可能下降
┌──────────────────────────────────────────┐

│ 在某些场景下，纯文本检索反而更准确          │
└──────────────────────────────────────────┘

挑战2: 跨模态检索能力仍不如纯文本检索
┌──────────────────────────────────────────┐
│ CLIP等模型的跨模态匹配精度有限             │
│ 尤其在细粒度语义匹配上表现不足              │
└──────────────────────────────────────────┘

挑战3: 数据格式多样性增加生成难度
┌──────────────────────────────────────────┐
│ 如何组织图像、表格、文本等多种格式数据       │
│ 如何清晰定义生成模块的输入格式              │
│ 如何避免多模态输入之间的冲突                │
└──────────────────────────────────────────┘
```

#### 6.6.4 MRAG 3.0：智能规划（Intelligent Planning）

##### 核心思想

MRAG 3.0是MRAG的最新演进，引入了三个革命性创新：**文档截图保留**、**多模态搜索规划**、**端到端多模态输出**。它标志着从"被动检索"到"智能规划"的范式转变。

```
MRAG 3.0 的三大创新：

创新1: 文档截图保留（Document Screenshot Retention）
  不再仅依赖OCR/解析，而是直接保留文档页面截图
  → 最小化信息损失，保留完整视觉上下文

创新2: 多模态搜索规划（Multimodal Search Planning）
  系统自主决定"是否需要检索"、"检索什么模态"、"如何重构查询"
  → 从被动检索转变为主动智能规划

创新3: 端到端多模态输出（End-to-End Multimodal Output）
  不仅输入是多模态的，输出也可以是多模态的
  → 文本+图像+表格的融合输出
```

##### 技术架构

```
MRAG 3.0 完整架构图：

═══════════════════════════════════════════════════════════
                    文档解析与索引
═══════════════════════════════════════════════════════════

  多模态文档（PDF/HTML/Word...）
      │
      ├──→ 提取式解析（与MRAG 2.0相同）
      │    ├── 文本块 → 文本嵌入模型 → 文本向量库
      │    └── 图像/表格 → 多模态嵌入模型 → 多模态向量库
      │
      └──→ 【新增】文档截图保留 ⭐
           ├── 文档页面截图
           ├── MLLM向量化编码（如ColPali）
           └── → 截图向量库（Documents/Screenshots Vector DB）

═══════════════════════════════════════════════════════════
                    多模态搜索规划 ⭐ （新模块）
═══════════════════════════════════════════════════════════

  用户多模态查询 Q = (q_text, q_image)
      │
      ▼
  ┌─────────────────────────────────────────┐
  │  检索分类（Retrieval Classification）      │
  │                                         │
  │  动态决策：是否需要检索？检索什么？        │
  │  动作空间 A = {none, text, image}        │
  │                                         │
  │  a* = argmax F_RC(a | Q, D)              │
  │  其中 D 为历史检索文档                    │
  │                                         │
  │  • 不需要检索 → 直接生成                  │
  │  • 文本检索 → 仅检索文本库                │
  │  • 图像检索 → 检索多模态库+截图库          │
  └─────────────────────────────────────────┘
      │
      ▼ (如果需要检索)
  ┌─────────────────────────────────────────┐
  │  查询重构（Query Reformulation）          │
  │                                         │
  │  Q* = F_QR(Q, D)                        │
  │                                         │
  │  • 整合视觉线索改进查询                   │
  │  • 处理代词引用（"这个图表"→具体描述）     │
  │  • 多跳场景：分解为原子子查询             │
  │    {q1*, q2*, ..., qn*}                  │
  └─────────────────────────────────────────┘

═══════════════════════════════════════════════════════════
                    多模态检索
═══════════════════════════════════════════════════════════

  规划后的查询
      │
      ├──→ 文本向量库检索（Text Vector DB）
      ├──→ 多模态向量库检索（Multimodal Vector DB）
      └──→ 截图向量库检索（Screenshots Vector DB）⭐
      │
      ▼
  检索结果融合

═══════════════════════════════════════════════════════════
                    多模态生成 ⭐ （增强）
═══════════════════════════════════════════════════════════

  检索结果 + 用户查询
      │
      ├──→ 纯文本查询 → LLM → 纯文本回答
      │
      └──→ 多模态查询 → MLLM → 多模态回答
           │
           ├── 输出方式1: 原生MLLM输出
           │   MLLM直接生成文本+图像描述
           │
           └── 输出方式2: 增强多模态输出 ⭐
               ├── 位置识别：在文本中找到插入多模态元素的最佳位置
               ├── 候选检索：从知识库检索相关图像/视频
               └── 匹配插入：选择最合适的多模态元素并插入
               → 最终输出：文本+图像+表格的融合回答
```

##### 核心技术组件详解

```
MRAG 3.0 的五大核心技术模块：

┌─────────────────────────────────────────────────┐
│ 模块1: 文档截图保留（Screenshot Retention）       │
├─────────────────────────────────────────────────┤
│                                                 │
│ 技术原理：                                       │
│ • 直接截取文档每一页的完整截图                    │
│ • 使用MLLM（如ColPali）对截图进行向量化编码       │
│ • 保留完整的视觉布局、图表、排版信息              │
│                                                 │
│ 为什么有效：                                     │
│ • OCR/解析总会有信息损失                         │
│ • 截图保留了"人看到的样子"                       │
│ • MLLM可以直接理解截图中的所有视觉元素            │
│                                                 │
│ 代表工作：                                       │
│ • ColPali（2024）：基于视觉语言模型的文档检索     │
│ • DSE（2024）：文档截图嵌入                       │
│ • LongVU（2024）：长文档视觉理解                  │
└─────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────┐
│ 模块2: 检索分类（Retrieval Classification）      │
├─────────────────────────────────────────────────┤
│                                                 │
│ 核心问题：是否需要检索？检索什么模态？             │
│                                                 │
│ 数学形式化：                                     │
│ 输入：多模态查询 Q = (q_text, q_image)           │
│ 动作空间：A = {a_none, a_text, a_image}          │
│ 最优策略：a* = argmax F_RC(a | Q, D)             │
│                                                 │
│ 决策逻辑：                                       │
│ ┌──────────────────────────────────────────┐    │
│ │ 查询类型          → 检索策略               │    │
│ │ "巴黎在哪里？"   → a_none（MLLM直接回答） │    │
│ │ "表1中的数据..."  → a_text（文本检索）     │    │
│ │ "这个图表的趋势"  → a_image（图像检索）    │    │
│ │ 多跳场景          → 动态多轮检索           │    │
│ └──────────────────────────────────────────┘    │
│                                                 │
│ 关键发现：                                       │
│ • 强制检索可能反而降低性能                        │
│   （检索到的图像可能引入误导信息）                │
│ • 动态路由比固定管线更优                          │
│ • 多跳场景需要累积知识决策                        │
└─────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────┐
│ 模块3: 查询重构（Query Reformulation）           │
├─────────────────────────────────────────────────┤
│                                                 │
│ 核心问题：如何改进用户查询以提高检索质量？         │
│                                                 │
│ 数学形式化：                                     │
│ Q* = F_QR(Q, D)                                 │
│                                                 │
│ 三种重构策略：                                   │
│                                                 │
│ 策略1: 视觉线索整合                              │
│   原始查询："这个图表显示了什么？"                 │
│   重构后："折线图显示2024年Q1-Q4的销售额变化      │
│          趋势，其中Q3有明显下降"                  │
│   （将视觉信息转化为精确文本描述）                │
│                                                 │
│ 策略2: 代词消解                                  │
│   原始查询："它的准确率是多少？"                   │
│   重构后："模型A在ImageNet数据集上的准确率"        │
│   （将代词替换为具体实体）                        │
│                                                 │
│ 策略3: 多跳分解                                  │
│   原始查询："图1中的方法和表2的基准对比如何？"     │
│   重构后：                                       │
│   q1* = "图1中的方法是什么？"                     │
│   q2* = "表2中的基准方法有哪些？"                 │
│   q3* = "方法X与基准Y的性能对比"                  │
│   （将复杂查询分解为原子子查询）                  │
└─────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────┐
│ 模块4: 多模态输出增强                            │
├─────────────────────────────────────────────────┤
│                                                 │
│ 两种输出方式：                                   │
│                                                 │
│ 方式1: 原生MLLM输出                              │
│   • MLLM直接生成包含多模态信息的回答              │
│   • 例如：描述图像内容、生成图表建议              │
│   • 优点：自然流畅                               │
│   • 缺点：可能产生幻觉                           │
│                                                 │
│ 方式2: 增强多模态输出 ⭐                         │
│   三步流程：                                     │
│   ┌─────────────────────────────────────┐       │
│   │ Step 1: 位置识别                     │       │
│   │ 在生成的文本中找到最佳插入点           │       │
│   │ "在'如图所示'处插入相关图像"          │       │
│   ├─────────────────────────────────────┤       │
│   │ Step 2: 候选检索                     │       │
│   │ 从知识库检索相关的图像/视频候选        │       │
│   │ 基于语义相关性和质量排序               │       │
│   ├─────────────────────────────────────┤       │
│   │ Step 3: 匹配插入                     │       │
│   │ 选择最匹配的多模态元素                 │       │
│   │ 插入到文本中的指定位置                 │       │
│   └─────────────────────────────────────┘       │
│   → 最终输出：图文并茂的融合回答                  │
└─────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────┐
│ 模块5: 三库并行检索                              │
├─────────────────────────────────────────────────┤
│                                                 │
│ MRAG 3.0 维护三个独立的向量数据库：               │
│                                                 │
│ 1. 文本向量库（Text Vector DB）                  │
│    • 存储文本块的嵌入向量                        │
│    • 使用文本嵌入模型（BGE/E5等）                │
│    • 用于文本语义检索                            │
│                                                 │
│ 2. 多模态向量库（Multimodal Vector DB）          │
│    • 存储图像/表格的嵌入向量                     │
│    • 使用多模态嵌入模型（CLIP等）                │
│    • 用于跨模态检索                              │
│                                                 │
│ 3. 截图向量库（Screenshots Vector DB）⭐        │
│    • 存储文档页面截图的嵌入向量                  │
│    • 使用MLLM向量化（ColPali等）                │
│    • 保留完整视觉上下文                          │
│                                                 │
│ 检索时：根据查询类型动态选择检索哪些库            │
└─────────────────────────────────────────────────┘
```

#### 6.6.6 MRAG演进的深层洞察

```
从MRAG 1.0到3.0的范式转变：

┌─────────────────────────────────────────────────────┐
│                                                     │
│  MRAG 1.0 → MRAG 2.0 → MRAG 3.0                    │
│                                                     │
│  模态转换    保留原始    智能规划                      │
│  (翻译)     (原生)     (Agent化)                     │
│                                                     │
│  ─────────────────────────────────────────          │
│                                                     │
│  核心转变：                                          │
│  • 从"工具型系统"到"自主智能体"                       │
│  • 从"被动检索"到"主动规划"                           │
│  • 从"文本为中心"到"模态无关"                         │
│  • 从"理解任务"到"理解+生成统一"                      │
│                                                     │
└─────────────────────────────────────────────────────┘

关键洞察：

1. 检索器正在变成Agent
   MRAG 3.0引入的搜索规划模块，使检索器不再是简单的
   "查询→返回结果"，而是能够自主决策"是否检索"、
   "检索什么"、"如何改进查询"的智能体。

2. 截图保留挑战了传统OCR范式
   MRAG 3.0的文档截图方法表明：与其费力解析文档结构，
   不如直接让MLLM"看"原始页面。这可能预示着
   文档理解的未来方向。

3. 多模态输出是真正的端到端
   MRAG 1.0/2.0的输出都是纯文本，只有MRAG 3.0
   实现了真正的端到端多模态（输入多模态→输出多模态）。

4. 但MRAG 3.0仍面临挑战
   • 所有模态投影到共享空间可能导致"语义漂移"
   • 计算成本显著增加
   • 多模态输出的质量评估标准尚未统一
```

#### 6.7.1 多模态RAG技术路线全景图

当前多模态RAG存在四条主要技术路线，从简单到复杂依次递进：

```
多模态RAG四条技术路线全景：

路线1: 文本翻译路线（Text-Translation）
═══════════════════════════════════════
  图像/表格 → VLM描述 → 纯文本 → 文本RAG
  代表：早期方案、LangChain多模态模板
  优点：实现最简单，兼容现有系统
  缺点：信息损失最大
  适合：快速原型、简单图文场景

路线2: 文本检索+多模态生成路线（Text-Retrieve + Multimodal-Generate）
═══════════════════════════════════════
  文本嵌入检索 → 获取文本+原始图像 → VLM直接处理 → 多模态回答
  代表：RAG-Anything VLM增强模式、GPT-4RAG
  优点：检索简单，生成阶段保留多模态信息
  缺点：检索仍依赖文本表示
  适合：文档问答、VQA

路线3: 多模态嵌入统一检索路线（Unified Multimodal Embedding）
═══════════════════════════════════════
  文档截图 → VLM编码 → 统一嵌入空间 → 跨模态检索 → VLM生成
  代表：ColPali、ColQwen2.5、BGE-VL、Nomic Embed Multimodal
  优点：端到端多模态，无OCR瓶颈，保留完整视觉信息
  缺点：需要GPU，索引成本高
  适合：复杂文档检索、视觉密集型场景 ⭐推荐

路线4: 智能规划路线（Agentic / Intelligent Planning）
═══════════════════════════════════════
  多模态查询 → 搜索规划Agent → 动态路由+检索 → 多模态生成+多模态输出
  代表：MRAG 3.0框架、Agentic Multimodal RAG
  优点：最智能，自主决策是否检索、检索什么
  缺点：系统最复杂，延迟最高
  适合：生产级多模态系统、复杂多跳推理
```

| 智能规划 | MRAG 3.0 | 动态路由 | MLLM+输出增强 | ⭐⭐⭐ 高 | ⭐⭐⭐ 复杂 |

##### ColPali：革命性的视觉文档检索模型 ⭐⭐⭐

ColPali是当前多模态RAG领域**最具影响力**的模型，它彻底改变了文档检索的方式。

```
ColPali 的核心创新：

传统方式（OCR流水线）：
  文档页面 → OCR → 文本提取 → 文本分块 → 文本嵌入 → 文本向量库
                    ↑                    ↑
              可能出错              可能割裂关键词

ColPali方式（端到端视觉）：
  文档页面截图 → VLM直接编码 → 多向量表示 → 视觉向量库
                    ↑
            保留完整视觉信息
            无OCR，无信息损失
```

**ColPali的架构原理**：

```
ColPali 架构图：
```

##### 路线2: 文本检索+多模态生成路线实现

```python
# 路线2: 文本检索 + VLM生成
import fitz  # PyMuPDF
from PIL import Image
import base64

class TextRetrieveVLMGenerate:
    def __init__(self):
        self.vectorstore = ...  # 文本向量库
        self.vlm = ChatOpenAI(model="gpt-4o")  # 多模态LLM

    def index_document(self, pdf_path):
        doc = fitz.open(pdf_path)
        for page_num, page in enumerate(doc):
            # 文本检索索引
            text = page.get_text()
            self.vectorstore.add_text(text, metadata={"page": page_num})

            # 保留原始页面图像
            pix = page.get_pixmap()
            img = Image.frombytes("RGB", [pix.width, pix.height], pix.samples)
            img.save(f"page_{page_num}.png")

    def query(self, question):
        # Step 1: 文本检索
        text_results = self.vectorstore.search(question, k=3)

        # Step 2: 获取对应页面的原始图像
        images = []
        for result in text_results:
            page_num = result.metadata["page"]
            img = Image.open(f"page_{page_num}.png")
            images.append(img)

        # Step 3: VLM直接处理图像+文本
        response = self.vlm.generate(
            prompt=question,
            images=images,  # 传入原始图像
            context=text_results
        )
        return response
```

##### 路线3: 多模态嵌入统一检索路线实现（推荐）⭐

```python
# 路线3: ColPali/ColQwen2 端到端多模态检索
from colpali.documents import Base64Image
from colpali.retrieval import ColPaliRetriever
from colpali.generation import ColPaliGenerator

class ColPaliRAG:
    """基于ColPali的端到端多模态RAG"""

    def __init__(self):
        # 初始化ColPali检索器
        self.retriever = ColPaliRetriever.from_pretrained(
            "vidore/colqwen2.5-v0.2"  # 使用ColQwen2.5（支持中文）
        )
        self.generator = ColPaliGenerator.from_pretrained(
            "Qwen/Qwen2.5-VL-7B-Instruct"
        )

    def index_documents(self, pdf_pages):
        """
        索引文档页面（直接使用截图）
        pdf_pages: List[PIL.Image] 文档每页的截图
        """
        # ColPali直接对页面截图编码，无需OCR！
        embeddings = self.retriever.encode_documents(pdf_pages)
        # 每个页面产生多个向量（多向量表示）
        self.vector_store.add(embeddings, pdf_pages)

    def retrieve(self, query, top_k=5):
        """
        多模态检索
        query: 文本查询
        """
        # 查询编码
        query_embedding = self.retriever.encode_query(query)

        # 晚期交互检索
        results = self.vector_store.search(query_embedding, top_k=top_k)

        # 返回相关的文档页面截图
        return results  # List[PIL.Image]

    def rag_query(self, question):
        """完整的RAG查询流程"""
        # Step 1: 检索相关页面
        relevant_pages = self.retrieve(question, top_k=3)

        # Step 2: VLM理解页面并生成答案
        answer = self.generator.generate(
            query=question,
            documents=relevant_pages  # 直接传入页面图像
        )

        return answer
```

```python
            "text": "这个图表的趋势如何？",
            "image": <PIL.Image>  # 可选的图像输入
        }
        """

        # Step 1: 搜索规划（智能决策）
        plan = self.planner.plan(multimodal_query)
        # plan = {
        #   "need_retrieval": True,
        #   "retrieval_type": "image",  # none/text/image
        #   "reformulated_query": "折线图显示的2024年销售趋势",
        #   "sub_queries": [...]  # 多跳场景
        # }

        if not plan["need_retrieval"]:
            # 不需要检索，直接用MLLM回答
            return self.generator.generate(multimodal_query)

        # Step 2: 根据规划执行检索
        if plan["retrieval_type"] == "text":
            results = self.text_vectorstore.search(
                plan["reformulated_query"], top_k=5
            )
        elif plan["retrieval_type"] == "image":
            # 同时检索多模态库和截图库
            mm_results = self.multimodal_vectorstore.search(
                plan["reformulated_query"], top_k=5
            )
            sc_results = self.screenshot_vectorstore.search(
                plan["reformulated_query"], top_k=3
            )
            results = self.fuse_results(mm_results, sc_results)

        # Step 3: 多模态生成（支持多模态输出）
        answer = self.generator.generate(
            query=multimodal_query,
            context=results,
            output_mode="multimodal"  # 输出可包含图像
        )

        return answer
```

### 6.8 核心问题深入：多模态知识统一记忆与检索

#### 6.8.1 三种实现范式对比

多模态RAG的实现存在三种主要范式，各有优劣：

```
范式一：文本翻译（Text-Translation）
──────────────────────────────────────
图像 → VLM描述 → 文本 → 纯文本RAG
表格 → 结构化文本 → 纯文本RAG
公式 → LaTeX文本 → 纯文本RAG

优点：实现简单，兼容现有文本RAG系统
缺点：信息瓶颈（非文本模态的独有信息丢失）
适用：快速原型、对视觉信息要求不高的场景

范式二：文本检索 + 多模态生成（Hybrid）
──────────────────────────────────────
查询 → 文本嵌入检索 → 获取相关文本 + 原始图像/表格
    → 多模态LLM直接处理原始多模态数据 → 生成回答

优点：检索简单，生成阶段保留多模态信息
缺点：检索质量仍依赖文本表示
适用：文档问答（VLM增强查询）

范式三：统一多模态检索（Unified Multimodal）
──────────────────────────────────────
查询 → 统一嵌入空间检索 → 直接获取多模态证据
    → 多模态LLM综合分析 → 生成回答

优点：最大语义保真度，支持任意模态查询
缺点：计算成本高，需要多模态编码器
适用：对准确性要求高的专业场景
```

| 维度 | 文本翻译 | 文本检索+多模态生成 | 统一多模态检索 |
|------|----------|---------------------|----------------|
| **实现复杂度** | ⭐ 低 | ⭐⭐ 中 | ⭐⭐⭐ 高 |
| **信息保真度** | ⭐ 低 | ⭐⭐ 中 | ⭐⭐⭐ 高 |
| **跨模态能力** | ❌ 无 | ⚠️ 有限 | ✅ 完整 |
| **计算成本** | ⭐ 低 | ⭐⭐ 中 | ⭐⭐⭐ 高 |
| **兼容性** | ✅ 现有系统 | ⚠️ 需要VLM | ❌ 需要专门架构 |
| **检索精度** | ⭐⭐ 中 | ⭐⭐ 中 | ⭐⭐⭐ 高 |

#### 6.8.2 多模态嵌入空间对齐技术

**对比学习（Contrastive Learning）** 是实现跨模态对齐的核心技术：

```
对比学习的训练过程：

正样本对（应该靠近）：
  [图像: 猫的照片] ←→ [文本: "一只橘色的猫坐在沙发上"]
  [表格: 准确率对比] ←→ [文本: "模型A准确率高于模型B"]

负样本对（应该远离）：
  [图像: 猫的照片] ←→ [文本: "今天的股市上涨了3%"]
  [图像: 猫的照片] ←→ [表格: 温度数据]

训练目标：
  最大化正样本对的相似度
  最小化负样本对的相似度

Loss = -log(exp(sim(I,T+)/τ) / Σ exp(sim(I,Ti)/τ))
         ↑ 正样本相似度              ↑ 所有样本相似度
```

```
CLIP模型的工作原理：

编码器架构：
┌──────────────┐     ┌──────────────┐
│  图像编码器   │     │  文本编码器   │
│  (ViT/ResNet)│     │  (Transformer)│
└──────┬───────┘     └──────┬───────┘
       │                     │
       ▼                     ▼
  图像嵌入向量           文本嵌入向量
  [0.12, -0.34, ...]    [0.15, -0.31, ...]
       │                     │
       └──────────┬──────────┘
                  ▼
          余弦相似度计算
          sim = 0.95 (高 → 匹配)
```

### 6.9 研究内容四：实验分析与系统集成验证

#### 6.9.1 评估指标体系

多模态RAG系统的评估需要覆盖多个维度：

```
评估指标框架：

1. 检索质量评估
   ├── 跨模态检索准确率（Cross-Modal Retrieval Accuracy）
   │   └── 文本查询→图像结果的准确率
   │   └── 图像查询→文本结果的准确率
   ├── Mean Reciprocal Rank (MRR)
   │   └── 第一个相关结果的排名倒数
   ├── Normalized Discounted Cumulative Gain (NDCG)
   │   └── 排序质量的综合评估
   └── 模态覆盖率（Modality Coverage）
       └── 检索结果是否覆盖所有相关模态

2. 生成质量评估
   ├── 多模态接地性（Multimodal Grounding）
   │   └── 生成内容是否基于检索到的多模态证据
   ├── 视觉理解准确性
   │   └── 对图表/表格的描述是否准确
   ├── 幻觉率（Hallucination Rate）
   │   └── 是否生成了检索证据不支持的内容
   └── 综合回答质量（人工评估）
       └── 专业领域人员的主观评分

3. 系统性能评估
   ├── 端到端延迟（End-to-End Latency）
   ├── 吞吐量（Queries Per Second）
   ├── 存储开销（多模态 vs 纯文本）
   └── 计算开销（GPU/CPU使用率）
```

## 9. 简单实现示例

### 9.1 基于LangChain的经典RAG
```python
# 安装依赖
# pip install langchain openai chromadb

from langchain.document_loaders import TextLoader
from langchain.text_splitter import RecursiveCharacterTextSplitter
from langchain.embeddings import OpenAIEmbeddings
from langchain.vectorstores import Chroma
from langchain.chat_models import ChatOpenAI
from langchain.chains import RetrievalQA

# 1. 加载文档
loader = TextLoader("your_document.txt")
documents = loader.load()

# 2. 文档分块
text_splitter = RecursiveCharacterTextSplitter(
    chunk_size=1000,
    chunk_overlap=200
)
chunks = text_splitter.split_documents(documents)

# 3. 向量化并存储
embeddings = OpenAIEmbeddings()
vectorstore = Chroma.from_documents(chunks, embeddings)

# 4. 创建检索问答链
llm = ChatOpenAI(model="gpt-3.5-turbo")
qa_chain = RetrievalQA.from_chain_type(
    llm=llm,
    chain_type="stuff",
    retriever=vectorstore.as_retriever()
)

# 5. 查询
query = "你的问题是什么？"
answer = qa_chain.run(query)
print(answer)
```

### 9.2 简单的GraphRAG示例概念
```python
# 概念性代码，展示GraphRAG的基本思路
class SimpleGraphRAG:
    def __init__(self, knowledge_graph, vector_store):
        self.kg = knowledge_graph  # 知识图谱
        self.vs = vector_store      # 向量存储
    
    def query(self, question):
        # 1. 实体识别
        entities = self.extract_entities(question)
        
        # 2. 在知识图谱中查找相关子图
        subgraph = self.kg.get_subgraph(entities)
        
        # 3. 结合向量检索
        vector_results = self.vs.search(question)
        
        # 4. 融合图结构信息和向量检索结果
        combined_context = self.fuse_results(subgraph, vector_results)
        
        # 5. 生成答案
        answer = self.generate_answer(question, combined_context)
        return answer
```

## 附录：常见问题解答

### Q1: RAG和微调（Fine-tuning）有什么区别？
**A**: 
- **RAG**：不修改模型，通过检索外部知识增强回答
- **微调**：修改模型参数，将知识"注入"模型
- **选择建议**：知识频繁更新用RAG，特定领域风格用微调

### Q2: RAG系统的主要挑战是什么？
**A**:
1. 检索质量：找到真正相关的信息
2. 上下文管理：处理长文档和大量检索结果
3. 幻觉控制：确保生成基于检索内容
4. 性能优化：平衡准确性和响应速度

### Q3: 如何评估RAG系统的效果？
**A**:
- **检索评估**：准确率、召回率、MRR
- **生成评估**：答案准确性、相关性、流畅性
- **端到端评估**：用户满意度、任务完成率

### Q4: RAG适合什么样的应用场景？
**A**:
- 需要最新信息的场景
- 需要引用来源的场景
- 知识库经常更新的场景
- 需要可解释性的场景
