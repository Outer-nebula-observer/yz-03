# 第一部分：构思——应用场景、问题发现与解决思路

> 先讲**我们在什么场景下、发现了什么问题、想到什么思路、沉淀出什么创新点**；具体的字段/门控/检索细节放到第二部分技术路线逐层展开。每节均标注「灵感来源 → 做到什么程度 → 预计效果」。

## 1.1 应用场景：场次制的作战规划智能体

**场景**：「智戎」大小模型协同平台上，大模型作战规划智能体承接规划任务。任务以**场次（session）**为单位到来，一个场次的完整生命周期是：

```
受领任务（目标/约束）→ 检索准备知识 → 产出作战方案 → AFSIM 推演反馈 → 复盘总结
```

场次可短至一次仓促防御、长至一场战役规划；智能体**连续经历许多场次**——这正是记忆发挥作用的舞台。

**这个场景对记忆提出三种天然形态**（应用场景本身决定了记忆系统该怎么设计）：

| 记忆形态 | 场景对应 | 例子 |
|---|---|---|
| 场内工作记忆 | 一场任务内的目标、约束、战报 | "限时 4 小时""南坡有反坦克火力点" |
| 跨场次经验 | 打过的仗留下的教训与对策 | "夜战未前置电子压制吃过亏" |
| 永久知识 | 装备参数、条令、地形 | "T-90 最大速度 60km/h" |

**设计映射**：部队参谋工作法"战前研究 → 战中处置 → 战后复盘"，恰好对应我们记忆系统的三段组织——**双库检索**（战前研究）、**短期槽位**（战中处置）、**复盘进化**（战后复盘）。场次制不是我们发明的约束，而是应用场景本身——**长短期记忆的分野由此而来**。

## 1.2 问题发现：没有记忆的规划智能体会怎样

对着上面的场景推演"智能体没有任何记忆系统"的后果，得到四个具体失败模式（后文每个技术决策都在回答其中一个）：

| # | 失败模式 | 具体表现 | 后果 |
|---|---|---|---|
| **P1** | 每场从零开始 | 第一场夜战吃了"未前置电子压制"的亏，第二场照犯 | 经验不积累，越用不变强 |
| **P2** | 场内信息超窗 | 战报持续流入，上下文窗口装不下；粗暴截断把"禁止越境"约束挤了出去 | 规划违反硬约束 |
| **P3** | 查询口径混杂 | 查"T-90 速度"需要参数级精确，查"夜战教训"需要语义泛化——单一检索两头不讨好 | 参数错一个数 / 教训召不回 |
| **P4** | 记忆库越攒越脏 | 复盘十次写十遍同一条教训；场次流水账混进知识库；说不清某条记忆哪来的 | 库越大越难用，且不可审计 |

## 1.3 构思思路：每个问题 → 论文启发 → 我们的方案

### P1 每场从零开始 → 七步闭环：把记忆做成可进化的回路

**论文启发**：讲义给的是"记忆形成/检索/进化"三段式，太抽象无法直接开发；RAG 只读不进化（解决不了 P1），Reflexion/TiM 证明"任务后反思固化经验"有效但只做了单点。

**我们的方案**：把三段式按**时间轴展开**成可执行的七步闭环——

```
①规划（建槽位·定目标约束）→ ②查询列表（显式化"我需要什么"）
→ ③检索（三路混合）→ ④装载（组装上下文）→ ⑤规划输出
→ ⑥AFSIM 推演反馈 → ⑦记忆进化（复盘沉淀）
        ↑______________________________|
```

- **为什么是闭环而非流水线**：⑦ 的产物（新经验）会改变 ③ 的输入（下场次检索命中）——demo 中 P002 场次召回的正是 P001 复盘写入的教训（`source: '复盘:P001'` 可溯源）。这个自增强回路就是"越用越强"的机制保证。
- **查询列表显式化（创新点 C）**：LLM 直接检索时"查什么"是隐式的、不可控的。我们让规划阶段先产出结构化查询列表（`QueryItem{intent, target, route, query_text}`），检索按列表执行、命中回填——**检索计划先于检索执行，事后可审计**。借鉴 ChatDB 的 Chain-of-Memory。

**做到什么程度 → 预计效果**：七步全链路已通（`pipeline.py` + WebUI 可演示）；自增强回路已有 demo 证据，量化验证靠消融 G3（场次数 vs 规划质量曲线）。

### P2 场内信息超窗 → MemGPT 分层槽位 + 确定性阈值改造

**论文启发**：候选三种——滑动窗口（太简单，丢约束风险）、摘要压缩（丢细节）、**MemGPT 分层**（working context 常驻 + FIFO 滚动 + 阈值归档）。选 MemGPT 因为它**天然区分"关键信息常驻"与"历史消息滚动"**，正好映射作战场景的"约束不可丢"与"战报可压缩"。

**我们的方案**：槽位分层 + 三个本地化改造（每处有代码注释标注）：

| MemGPT 原设计 | 我们的改造 | 为什么改 |
|---|---|---|
| LLM 自主决定换页（函数调用） | **确定性阈值**（70% 预警 / 100% flush） | 消融实验要求可复现；LLM 换页不可测试 |
| 分页决策靠系统提示引导 | 阈值化为 `memory_pressure` 只读属性 | 一行断言即可测试 |
| flush 出的消息进 recall storage 即止 | **归档并入复盘材料** | 否则被压缩的信息永远失去晋升机会 |

第三个改造来自读论文源码时发现的"缝合缺口"：MemGPT 只管压缩不管沉淀，TiM 只管复盘不管压缩——被压缩掉的信息成了孤岛。`close_session()` 里把 `archived` 拼进复盘材料，一行代码补上这条缝。

**做到什么程度 → 预计效果**：已实现；4000 token 预算内作战约束永不因压缩丢失（测试断言锁定）。

### P3 查询口径混杂 → 三路混合检索，按查询特点路由

**论文启发**：MIRIX 的多策略路由（按查询特点自主选路）、ChatDB 的符号查询（数据库即记忆）、ExpeL 的向量召回（经验轨迹）。

**我们的方案**：作战查询天然分三类，各走最优路径——

| 查询类型 | 例子 | 最优路径 | 为什么 |
|---|---|---|---|
| 语义相似 | "夜战教训" | vector | "夜战吃亏"≠字面重叠，需语义泛化 |
| 型号代号 | "T-90" | bm25 | 向量对专有名词反而不稳，字面最准 |
| 参数精确 | "红方坦克破甲厚度" | sql | 需要确定性答案，向量给不出"参数级" |

三路各自归一化（cosine→[0,1]、BM25→max 归一、SQL 恒 1.0）后加权融合，权重 α/β/γ 是消融 G5 的扫描点；**外加 min_score 阈值**（借鉴 ExpeL/Mem-α/MemP 三家源码共有的细节）：低分结果不返回——噪声进上下文比漏召回更伤。

**做到什么程度 → 预计效果**：三路 + 融合 + min_score 已实现；预期参数级查询零容错命中、教训跨措辞召回（G0/G2 指标）。

### P4 记忆越攒越脏 → 建议执行分离的四操作进化

**论文启发**：PREMem 的 θ 查重（链接对判重）、MemoryBank 的艾宾浩斯遗忘（R=e^(-t/S)）、Reflexion 的语言化反思、TiM 的 Post-thinking 抽象。

**我们的方案**：核心原则——**LLM 只建议，代码执行**：

```
复盘文本 → LLM 抽取建议 [{op:write, type:experience, content:...}]   ← 建议侧（可换真模型/RL）
        → 代码执行：查重门控 → 写入 → 相邻合并 → 遗忘扫描 → 教训抽象   ← 执行侧（确定性、可回放）
```

**为什么分离**：作战复盘必须可审计——"为什么删了这条记忆？谁决定的？"全 LLM 黑盒无法回答。分离后每次进化产出 `EvolutionReport`（四操作计数 + 拒绝原因），消融实验直接统计此对象。

**四操作各自的论文依据与本地化**：

| 操作 | 论文来源 | 我们的改造 |
|---|---|---|
| 写入 | PREMem 链接对 θ | θ=0.80（MockEmbedding 分布偏高；接真模型回调 0.6，注释写明） |
| 合并 | TiM merge / Memp Add⊖Del⊕Update | `merged_from` 记录来源，可回放 |
| 遗忘 | MemoryBank R=e^(-t/S) | **加"失败教训保护线"**（importance≥2 永不遗忘）——论文没有，来自"作战失败不能忘"的领域常识 |
| 抽象 | TiM Post-thinking / StructMem 周期整合 | 本场新经验 ≥2 条触发（替代事件计数启发式） |

**做到什么程度 → 预计效果**：四操作 + 门控 + 审计全部落地；长期库"越用越干净"、每次写入可回放（G4）。

# 第二部分：技术路线——方案总述与逐层分述

## 2.1 方案总述

**一句话方案**：给「智戎」规划智能体外挂一套**两层四模块**的记忆系统——**短期槽位**管"本场规划的上下文资源调度"（场生场灭），**长期双库**管"跨场次的知识沉淀与召回"（越用越强）；两层之间只留一条**复盘晋升**通道，由三道门控强制；系统按**七步闭环**运行，每步产出可审计、可评测。

### 整体流程走查：一个场次的完整生命周期（七步闭环）

以"夜间夺占 2 号高地"为例，系统从头到尾走一遍：

```
【开场】指挥员下达任务："夜间夺占 2 号高地"
   ↓
① 建短期槽位：goal=夺占 2 号高地，约束=[禁止越境, 限时 4 小时]（🔒 不可压缩）
   ↓
② 生成查询列表："我需要什么知识？"——[查 2 号高地地形(fact/vector),
   召回夜战教训(experience/bm25)]（检索计划显式化，可审计）
   ↓
③ 执行检索：两库各自检索 → 三路融合重排 → 低分噪声过滤
   ↓
④ 装载登记：命中的地形事实 + 夜战教训写进短期槽位，逐条登记溯源
   （来自哪个库、哪场沉淀、召回过几次）
   ↓
⑤ 渲染上下文：目标 + 约束 + 装载记忆 + 近期战报 → 注入规划 LLM
   → LLM 产出作战方案
   ↓
⑥ 场次进行中：战报/中间结果持续推入 FIFO 消息队列
   （超 70% 预警 → 超容量自动 flush：旧消息压缩成摘要，存档不丢）
   ↓
【复盘时刻】任务结束，指挥员/系统给出复盘总结——**这就是"复盘"**
   ↓
⑦ 记忆进化：复盘文本 → LLM 抽取候选（教训/经验/参数）→ 三道门控
   （G1 复盘驱动✓ → G2 类别模板✓ → G3 θ查重✓）→ 通过者写入长期库
   → 场次关闭，短期槽位随场次结束而失效
   ↓
【下场次】再打 2 号高地时，②的查询自动召回本场⑦沉淀的教训
   ——这就是"越用越强"的自增强回路
```

**三个关键时间点**：

| 时间点 | 发生什么 | 为什么重要 |
|---|---|---|
| **开场（①②）** | 建槽位、生成查询列表 | 短期记忆场生场灭的起点；查询显式化=可审计 |
| **满载（flush）** | FIFO 超容量自动压缩旧消息 | 约束🔒永不压缩；被压缩内容存档并入复盘材料（不丢） |
| **复盘（⑦）** | 场次结束后的总结与沉淀 | 短期→长期**唯一**通道；系统"变强"的唯一时刻 |

**"复盘"是什么**：复盘 = 场次结束后，对本次任务执行情况做的**结构化总结**——包含三要素：**结果**（任务达成度）、**教训**（哪里做错了、为什么）、**经验**（下次怎么做更好）。在我们的系统里，复盘文本是记忆进化的**唯一输入**：只有复盘里被抽取出的"教训/经验"才能通过三道门控写入长期库，供后续场次检索复用。灵感来自部队"战后复盘"制度与 TiM 论文的 Post-thinking（任务后反思固化经验）——**这正是"短期记忆如何变成长期记忆"的答案**。

### 分层职责一句话

| 层 | 模块 | 一句话职责 |
|---|---|---|
| 模型 | `schema.py` | 统一数据模型（单一事实源；两把尺子的类型化） |
| 能力 | `short_term/` · `long_term/` · `retrieval/` · `evolution/` | 四模块互不 import，只经 schema 数据对象交互 |
| 边界 | `boundary.py` | 跨切面门控与审计（短期→长期的唯一合法通道） |
| 编排 | `controller.py` · `pipeline.py` | 调度（SCM：何时读/写/归档）+ 七步闭环编排 |

**后续分述路线**：2.2 记忆定义与定位 → 2.3 长短判据（两把尺子）→ 2.4 边界执行（三道门）→ 2.5 内容分类学（信息归哪类）→ 2.6 字段级放置蓝图（进容器放哪个字段）。

## 2.2 我们如何定义"记忆"

**工作定义**：记忆是为决策智能体服务的**可演化的外部知识库**——它在智能体与环境的持续交互中积累信息，并能被主动地写入、检索、修改与淘汰，最终目的是**让规划行为随经验变强**。

我们刻意区分三个常被混淆的概念：

| 概念 | 本质 | 与我们的关系 |
|---|---|---|
| **大模型记忆** | 干预模型内部状态（长上下文、KV 缓存、注意力改造） | 不是我们做的——那是"把窗口变大" |
| **RAG** | 静态外部知识供给 | 只是我们的子集——RAG 只读不进化 |
| **智能体记忆** | 可演化的外部记忆库（读 + 写 + 进化） | **我们的定位**——核心差异在"进化" |

> 一句话：**上下文工程管"窗口内的资源调度"，我们管"跨时间的认知连续性"。**

> 📌 **本节灵感来源**：三概念区分来自 21 篇精读的总体把握（尤其 Zep 对 episode 记忆的论述、MemGPT 对"外部记忆分层"的主张）。
> 📌 **做到什么程度**：定位已落成代码边界——`memsys` 只做外部记忆库，不改模型内部。
> 📌 **预计效果**：规划质量随场次累积提升，而非靠更大窗口的一次性容量。

## 2.3 如何区分长期与短期记忆——我们的"两把尺子"判据

这是整个系统设计的**第一决策**。我们不用"存在哪个数据库"这种工程视角区分，而用两条认知判据（对应讲义 18.1 节），并把它们**写进类型系统强制执行**：

| 尺子 | 短期 / 工作记忆 | 长期记忆 |
|---|---|---|
| **① 来源** | 单场次内产生（本次规划的目标、约束、消息、中间结果） | 跨场次沉淀（历史战例、装备参数、历史教训） |
| **② 时间尺度** | 场次结束即失效（归档后可晋升） | 持久存在，带衰减与强化机制 |

**落地为代码**（`memsys/schema.py`）：
- 短期 = `WorkingMemorySlot`（场次 ID 绑定，`status: open/closed`）
- 长期 = `MemoryEntry`（带 `timestamp / decay_strength / recall_count` 三个遗忘模型字段）

**为什么这样设计**：边界若只靠"约定"，开发中必然混乱（经验随手塞短期、事实漏进长期）。把两把尺子编码进数据结构，边界就从"文档纪律"变成"类型约束"。

> 📌 **本节灵感来源**：两把尺子（来源×时间尺度）直接对齐讲义 18.1 的认知判据；"判据写进类型系统"的做法受 Zep"非损式 episode + 侧挂语义"的数据建模启发。
> 📌 **做到什么程度**：已类型化（`WorkingMemorySlot` / `MemoryEntry`），并有 `boundary.py` 判定表强制（见 2.4/2.6.3）。
> 📌 **预计效果**：消融 G1（有/无边界）可量化"边界带来的库纯净度差异"。

## 2.4 边界执行：三道门控（不是靠自觉）

定义了边界，还要**强制执行**。我们实现了专门的边界模块（`memsys/boundary.py`），设三道门：

```
G1 复盘驱动门：短期内容唯一合法的晋升通道是"场次复盘"——
              不允许规划中途随手把消息写进长期库
G2 类别模板门：复盘候选必须命中"事实/经验"内容模板——
              纯场次流水账（"我方 3 营集结"）被拒绝，留在短期归档（不丢失）
G3 θ 查重门： 与长期库已有内容余弦相似度超过 θ（theta，相似度阈值，
              论文里习惯用这个希腊字母表示）判为重复，拒绝写入——
              防止同一条教训复盘十次就写十遍
```

**每道门的决策都进审计日志**（`boundary.audit_log()`），WebUI 可实时查看"什么内容被放行/拒绝、为什么"——边界执行全程可查，不依赖任何口头保证。

> 📌 **本节灵感来源**：G1"复盘才能沉淀"来自 TiM 的 Post-thinking（事后反思固化经验）；G2 类别门对应 MemSkill 的操作类型约束；G3 θ 查重来自 PREMem 的链接对判重（θ 取 0.80，接真模型回调 0.6）。
> 📌 **做到什么程度**：三道门全部代码强制 + 审计日志；G2 目前是关键词模板（Mock），接口已留 LLM 分类替换位。
> 📌 **预计效果**：长期库不被场次流水账污染（重复率、噪声率可测）；每次写入决策可回放（G4）。

## 2.5 作战信息如何分类录入——我们的内容分类学

我们按**内容性质**而非来源渠道决定录入哪个库：

| 作战信息 | 归类 | 录入路径 | 存储形态 |
|---|---|---|---|
| 装备参数（T-90 最大速度 60km/h） | 事实·参数级 | 知识库导入 + 复盘抽取 | 事实库（SQLite 行 + 属性键值） |
| 条令/交战规则 | 事实·稳定 | 知识库导入 | 事实库（`domain: semantic` 标签） |
| 地形/道路/气象 | 事实·环境 | 复盘抽取 + 导入 | 事实库（带 timestamp = 情景事实） |
| 战例经过（本场发生了什么） | **场次内容** | **不直接入长期库**——复盘时若命中教训模板才晋升 | 短期归档 → 晋升门控 |
| 成败教训（夜战未前置电子压制） | 经验·教训 | 复盘抽取（关键词"教训/失败"→ importance 2.0） | 经验库（向量 + 重要性加权） |
| 可复用对策（预备队提前 10 分钟投入） | 经验·对策 | 复盘抽取 | 经验库（`domain: procedural` 标签） |

**为什么长期记忆要建"双库"**：

> **"双库"= 事实库 + 经验库两个长期记忆库**。不是把数据存两份，而是**按信息的性质分家**：客观事实进事实库，主观教训进经验库，各自用最适合自己的存法和检索方式。

这个分法不是我们发明的——认知科学里早有对应：人脑的**陈述性记忆**（"是什么"：巴黎是法国首都、T-90 速度 60km/h）与**程序性记忆**（"怎么做"：骑自行车、夜战要先派侦察）就是两套系统，存储区与遗忘规律都不同。作战场景恰好同构：

| | 事实库（陈述性："是什么"） | 经验库（程序性："怎么做"） |
|---|---|---|
| 典型内容 | "T-90 最大速度 60km/h" | "夜间突袭要前置电子压制" |
| 查询时问的是 | **参数值**——差一个数就错 | **该怎么做**——意思对就行 |
| 最怕 | 检索回来一个"差不多"的数（67km/h 是 M1A2 的） | 字面不同就漏召回（"夜战吃亏"查不到"夜间遭伏击"） |
| 所以需要 | **精确匹配**：SQLite 行存 + 属性过滤 | **语义泛化**：向量相似度召回 |

**如果只用一个库会怎样**：
- 用向量库存事实 → "T-90 速度"可能召回到"M1A2 速度 67km/h"（语义相近但数值是错的）——**作战参数错一个数就是重大事故**；
- 用数据库存经验 → "夜战吃过亏"检索不到"夜间突袭遭伏击"（无共同关键词）——**教训白存了**；
- 所以双库不是存储冗余，是**两类检索需求互斥**的必然结果。

> 📌 **本节灵感来源**：内容分类学对齐讲义 18.1 与认知科学"陈述性/程序性"二分；事实库选型受 ChatDB（用数据库当符号记忆）启发，经验库受 ExpeL（从轨迹抽经验库）与 Reflexion（语言化反思）启发。
> 📌 **做到什么程度**：六类信息的录入路径全部落地；双库实现完整（SQLite + 向量索引）且接口统一（`BaseLongTermStore`，换底层存储不改业务代码）。
> 📌 **预计效果**：参数级查询精确命中（G0 指标）、教训跨措辞召回（G2 指标）；WebUI 双库浏览可现场验证。

## 2.6 字段级放置蓝图：进了容器放在哪（对齐代码）

> 2.5 回答"**信息归哪类**"，本节回答"**进了容器放哪个字段**"——把 `schema.py` / `working_memory.py` / 双库 / `boundary.py` 的放置规则一次讲清。

### 2.6.1 短期容器 `WorkingMemorySlot`：一场一槽，11 字段各司其职

组织范式借鉴 **MemGPT**（一篇把 LLM 上下文当"操作系统内存"管理的论文：常用信息放内存/常驻区，不常用的换页出去）——`working_context` 常驻 + `fifo_queue` 滚动；**一个规划场次绑定一个槽位**：

| 字段 | 放什么 | 压缩待遇 |
|---|---|---|
| `goal` / `constraints` | 本次规划目标、作战约束 | 🔒 **永不被删**（约束被压缩破坏 = 规划出错） |
| `working_context` | 高频关键信息常驻区 | 最后才动它 |
| `fifo_queue` | 消息/战报滚动队列（最旧先出） | **主要压缩对象** |
| `query_list` | ② 检索计划（`QueryItem{intent, target, route, query_text, answer_memory_ids}`，命中回填） | 不压缩——它是审计对象 |
| `loaded_memory` | ④ 已装载长期记忆 id 登记（溯源 + 消融统计） | — |
| `intermediate_results` | 管线中间结果（分析/生成/比较各步产物） | — |
| `plan_id` / `status` / 时间戳 | 场次身份与生命周期（`open/closed`，`touch()` 统一刷新） | — |

**容量与换页**（`working_memory.py`）：`capacity_tokens=4000`（简化计量：1 中文字≈1 token）→ **70% 预警** `memory_pressure=True`（SCM 论文——另一篇"自控记忆"工作——的预警思想，上层可提前归档）→ **100% flush**：驱逐最旧 ~50% → "旧递归摘要 + 被驱逐消息"→ 新摘要（≤120 词）→ 存 `archived` **不丢**，`close_session()` 时并入复盘材料（即 1.3 节 P2 的第三个改造）。

**渲染顺序**（`render()`）：头部 目标/约束 → 历史摘要 → 关键信息 → 查询列表 → 尾部 最近 20 条消息——关键信息永远在**首尾**（LongLLMLingua 论文的位置偏置结论：长提示里开头和结尾的信息，模型记得最牢）。

**压缩三档**（`compression.py` 策略类 + `get_strategy(name)` 工厂，G1 消融一行切换）：`truncate`（截断·MVP 零依赖）→ `summarize`（LLM 摘要）→ `llmlingua`（删 token 式压缩，延迟导入适配器已预留）。

### 2.6.2 长期容器 `MemoryEntry`：13 字段统一条目，进哪个库看类型

> **先把"双库"说人话**（2.5 讲了为什么分家，这里讲分家后怎么住）：
> - **"双库"指长期记忆的两个库**——**事实库**（`FactualStore`，SQLite 数据库）和**经验库**（`ExperientialStore`，向量索引）；
> - 两库**共用同一种"条目格式"** `MemoryEntry`（就像两个仓库用同一种货架标签）——所以字段表只有一张；
> - **同一条信息只会进其中一个库**：`type=fact` 进事实库、`type=experience` 进经验库，由 2.6.3 的判定表决定；
> - **差别只在"仓库设施"**：事实库配了"精确查找的抽屉"（属性过滤），经验库配了"按相似度找的感应器"（向量检索）——条目格式相同、检索设施各配各的。

字段按用途分四组（这张表两库通用）：

| 字段组 | 字段 | 服务什么 |
|---|---|---|
| 本体（3） | `id`（形如 `fact-1a2b3c4d`）/ `type` / `content` | 条目识别与正文 |
| 溯源（3） | `source` / `session_id` / `timestamp` | 创新点 E：每条注入规划的记忆可回查来历 |
| 遗忘模型（4） | `importance`（S 初值 + 保护线判据）/ `decay_strength`（S，召回 +1）/ `recall_count` / `last_recalled_at`（t 起点） | MemoryBank 艾宾浩斯遗忘曲线（见下方白话版） |
| 进化回放（3） | `merged_from` / `op_history` / `metadata` | G4 消融可重演"记忆怎么来的"；`metadata` 承载事实库属性键值 |

> **遗忘公式白话版**：`R = e^(-t/S)`——R 是"这条记忆还剩多少"（留存率），t 是"多久没被用"（距上次召回的时间），S 是"记忆强度"（每被召回一次 +1）。**翻译**：越久不用的记忆衰减越快（先快后慢，艾宾浩斯曲线）；但每被用一次就"巩固"一次、更难忘——这就是"常用教训自动留存、没人用的教训自然淘汰"，不需要人工清理。

**双库形态差异**（同一接口 `BaseLongTermStore`，读/写方法分两段——"检索只读、进化只写"的接口化；即"条目格式一张表、仓库设施两套配置"）：

| 维度 | 事实库 `FactualStore` | 经验库 `ExperientialStore` |
|---|---|---|
| 存储 | SQLite 单文件行存（12 列，`attrs_json` 属性键值） | 内存 dict + 向量索引（接口留 FAISS 持久化位） |
| 检索主路 | `search_attrs()` 属性精确过滤（**参数级**，ChatDB 符号查询 MVP） | 向量语义召回（编码 = 正文 + source，带情境） |
| 打分 | 向量 cosine 主 + 关键词 LIKE 兜底（命中记 1.0） | `0.8×cosine + 0.2×min(importance/3, 1)`——重要教训更易浮出（Reflexion：失败学得最多） |
| 命中强化 | `persist_recall()` 回写 SQLite（防重启丢失） | 内存即时生效（方法保留仅为接口对称） |
| 论文依据 | ChatDB（数据库即符号记忆） | ExpeL（轨迹召回）+ Reflexion（语言经验） |

> **强化统一时点**：`mark_recalled()`（S+1、t 重置）只在三路融合排序后执行**一次**——否则三路互检会让同一记忆 `recall_count` 虚涨 3 倍、艾宾浩斯模型失真（4.2 节 B2 修复）。

### 2.6.3 放置判定表 + 双向禁止（`boundary.py`——"表即文档"）

2.5 的分类学在代码里落成**六行判定表** `CONTENT_RULES`（新增内容类别只需加一行；两把尺子的取值由表带出）：

| 内容类别 | 归属层 | 尺子A·来源 | 尺子B·时间 |
|---|---|---|---|
| `goal`（本场规划目标） | 短期 only | 任务内 | 场次生命周期 |
| `constraint`（本场作战约束） | 短期 only | 任务内 | 场次生命周期 |
| `message`（场次消息/中间结果） | 短期 only | 任务内 | 场次生命周期 |
| `fact_param`（装备参数/条令条款） | 长期·事实 | 跨任务 | 持久 |
| `fact_event`（战例客观经过） | 长期·事实 | 跨任务 | 持久 |
| `experience`（成败教训/可复用对策） | 长期·经验 | 跨任务 | 持久 |

**双向禁止**（边界的强制力，不靠自觉）：
- **短期 → 长期**：场中直写长期一律被 `check_write()` 拒绝；唯一合法通道是复盘晋升 `promote()`（G1–G3 门控，见 2.4）；
- **长期 → 短期**：只能以检索结果形态进入（`retrieve → load_memory` 登记），`validate_load()` 拦"整段拷进 FIFO"——"检索只读、进化只写"的解耦不被绕过。

**晋升模板关键词**（G2 的 Mock 实现 `PROMOTION_PATTERNS`；接真模型换 LLM 分类，接口不变）：
- 事实：参数 / 条令 / 海拔 / 编制 / 性能 / 射程 / 速度 / 态势 / 部署
- 经验：教训 / 经验 / 对策 / 失败 / 成功 / 复盘 / 下次 / 应当 / 避免

### 2.6.4 与讲义"三类记忆内容"的对应（docs/03 §16.2 / §18.1）

| 讲义分类（代表工作） | 我们的落位 |
|---|---|
| ① 同一任务内的历史交互（Generative Agent / MemoChat / TiM / Voyager） | 短期槽位全部字段 + flush 归档（并入复盘材料） |
| ② 跨任务的经验（Reflexion / Synapse / ExpeL） | 经验库——复盘晋升写入，跨场次语义召回 |
| ③ 外部知识（ReAct / GITM） | 事实库——知识库导入，受智戎**知识锚定**约束（库外经验不许混入） |

讲义 18.1"短期→长期转换用**反思与抽象**" → 我们的复盘驱动晋升（G1）+ `abstract()` 教训抽象（1.3 节 P4 的四操作）。

> 📌 **本节灵感来源**（放置蓝图整体）：槽位分层 = MemGPT；双库形态 = ChatDB（符号）+ ExpeL（向量）；遗忘字段组 = MemoryBank（艾宾浩斯 R=e^(-t/S)）；渲染首尾原则 = LongLLMLingua（位置偏置）。
> 📌 **做到什么程度**：字段全部落地并有注释溯源；压缩三档中 `truncate`/`summarize` 可用，`llmlingua` 为预留接口。
> 📌 **预计效果**：这张蓝图让"任何一条信息放哪、为什么"都可指着代码回答——是 G1–G5 全部消融实验的实现基础。

# 第三部分：实现路径与耦合方式

## 3.1 分层解耦——模块如何协作

```
┌─ pipeline.py ──── 七步编排（只管流程顺序，不含业务逻辑）
├─ controller.py ── 总调度（唯一同时碰四模块的角色；SCM 思想）
├─ boundary.py ──── 三道门控 + 审计（跨切面，被 evolution 调用）
├──────────────────────────────────────────────
│  short_term/  working_memory + 压缩策略        │ 四大能力模块：
│  long_term/   factual(SQLite) + experiential(向量) │ 互相不 import 对方，
│  retrieval/   bm25 + hybrid(三路融合)          │ 只通过 schema 数据对象交互
│  evolution/   四操作 + 复盘驱动入口             │
├──────────────────────────────────────────────
│  schema.py ──── 统一数据模型（单一事实源）        │
│  llm.py / embeddings.py ── 外部能力抽象          │
│      （MockLLM/MockEmbedding 离线可跑；OpenAI 兼容骨架随时切换）
└──────────────────────────────────────────────
```

**耦合规则**（写在 `long_term/base.py` 接口注释里）：
1. **检索只读、进化只写**——独立评测互不污染
2. 依赖注入：`MemoryController(llm=?, embedding=?, ...)` 全可替换——Mock 与真模型**业务代码零改动**
3. 数据模型改动只从 `schema.py` 出发——单一事实源

单页控制台按**「输入 → 运行过程 → 产出」三区布局**，完整映射七步闭环；页首是**七步进度条**（当前场次推进到哪步、哪步已完成，一眼可见）：

- **左栏·输入区（📥）**：①开场表单 → ③④检索按钮 → 消息推入 → ⑥⑦复盘表单
- **中栏·运行过程（⚙️）**：
  - **运行事件流**：每次输入/产出实时配对记录（含场次分隔线）——"我输入了什么、系统产出了什么"逐条可讲；
  - **短期记忆·本场工作记忆构成**：目标/约束（🔒不可压缩徽标）/查询列表/已装载长期记忆（逐条溯源）/FIFO 消息流/归档摘要，顶部**容量水位条**（70% 预警线 + flush 线，超线变红）；
  - **⑤ 上下文实时渲染**（注入规划 LLM 的最终形态）。
- **右栏·产出（📦）**：检索命中（含溯源与创新点 E）→ 进化报告（本场沉淀了哪些记忆 id）→ **场次历史**（多轮沉淀主线：每场目标/耗时/写入/复用）→ 双库浏览（retention/召回次数/来源场次，支持按重要性/召回/留存/时间排序）→ 边界审计日志。

- **场景库**（5 个预置场景，覆盖五种演示目的）：标准闭环 / **第二夜·再战 2 号高地（跨场次复用）** / 教训复用 / 容量压缩（20 条消息灌爆触发 flush）/ 精确检索（sql 路）
- **一键填充**：选场景自动填全部表单（目标/约束/查询列表/消息流/复盘）
- **自动演示**：一键代点 ①→⑦ 全部按钮，每步停顿便于讲解
- **连续两场演示（沉淀→复用）**：一键跑完两场——第一场复盘沉淀"电子压制/预备队"教训，第二场开场检索即召回**往场沉淀**（复用横幅 + 场次历史 + 命中列表三处可见"⏪ 往场"徽标）——长期记忆的多轮生效有直观证据

**质量保障**：48 项 API 全链路自测（`webui/_selftest.py`，含跨场次复用断言）全绿；启动时自动 seed（幂等），开箱即玩。
