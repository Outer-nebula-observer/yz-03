# 第一部分：概念与定义（老师最关心的"是什么"）

## 1.1 我们如何定义"记忆"

**工作定义**：记忆是为决策智能体服务的**可演化的外部知识库**——它在智能体与环境的持续交互中积累信息，并能被主动地写入、检索、修改与淘汰，最终目的是**让规划行为随经验变强**。

我们刻意区分三个常被混淆的概念：

| 概念 | 本质 | 与我们的关系 |
|---|---|---|
| **大模型记忆** | 干预模型内部状态（长上下文、KV 缓存、注意力改造） | 不是我们做的——那是"把窗口变大" |
| **RAG** | 静态外部知识供给 | 只是我们的子集——RAG 只读不进化 |
| **智能体记忆** | 可演化的外部记忆库（读 + 写 + 进化） | **我们的定位**——核心差异在"进化" |

> 一句话：**上下文工程管"窗口内的资源调度"，我们管"跨时间的认知连续性"。**

## 1.2 如何区分长期与短期记忆——我们的"两把尺子"判据

这是整个系统设计的**第一决策**。我们不用"存在哪个数据库"这种工程视角区分，而用两条认知判据（对应讲义 18.1 节），并把它们**写进类型系统强制执行**：

| 尺子 | 短期 / 工作记忆 | 长期记忆 |
|---|---|---|
| **① 来源** | 单场次内产生（本次规划的目标、约束、消息、中间结果） | 跨场次沉淀（历史战例、装备参数、历史教训） |
| **② 时间尺度** | 场次结束即失效（归档后可晋升） | 持久存在，带衰减与强化机制 |

**落地为代码**（`memsys/schema.py`）：
- 短期 = `WorkingMemorySlot`（场次 ID 绑定，`status: open/closed`）
- 长期 = `MemoryEntry`（带 `timestamp / decay_strength / recall_count` 三个遗忘模型字段）

**为什么这样设计**：边界若只靠"约定"，开发中必然混乱（经验随手塞短期、事实漏进长期）。把两把尺子编码进数据结构，边界就从"文档纪律"变成"类型约束"。

## 1.3 边界执行：三道门控（不是靠自觉）

定义了边界，还要**强制执行**。我们实现了专门的边界模块（`memsys/boundary.py`），设三道门：

```
G1 复盘驱动门：短期内容唯一合法的晋升通道是"场次复盘"——
              不允许规划中途随手把消息写进长期库
G2 类别模板门：复盘候选必须命中"事实/经验"内容模板——
              纯场次流水账（"我方 3 营集结"）被拒绝，留在短期归档（不丢失）
G3 θ 查重门： 与长期库已有内容余弦相似度 > θ 判为重复，拒绝写入
```

**每道门的决策都进审计日志**（`boundary.audit_log()`），WebUI 可实时查看"什么内容被放行/拒绝、为什么"——这直接回答了老师可能问的"你怎么保证边界不被绕过"。

## 1.4 作战信息如何分类录入——我们的内容分类学

我们按**内容性质**而非来源渠道决定录入哪个库：

| 作战信息 | 归类 | 录入路径 | 存储形态 |
|---|---|---|---|
| 装备参数（T-90 最大速度 60km/h） | 事实·参数级 | 知识库导入 + 复盘抽取 | 事实库（SQLite 行 + 属性键值） |
| 条令/交战规则 | 事实·稳定 | 知识库导入 | 事实库（`domain: semantic` 标签） |
| 地形/道路/气象 | 事实·环境 | 复盘抽取 + 导入 | 事实库（带 timestamp = 情景事实） |
| 战例经过（本场发生了什么） | **场次内容** | **不直接入长期库**——复盘时若命中教训模板才晋升 | 短期归档 → 晋升门控 |
| 成败教训（夜战未前置电子压制） | 经验·教训 | 复盘抽取（关键词"教训/失败"→ importance 2.0） | 经验库（向量 + 重要性加权） |
| 可复用对策（预备队提前 10 分钟投入） | 经验·对策 | 复盘抽取 | 经验库（`domain: procedural` 标签） |

**为什么事实与经验分两个库**（第一部分最重要的设计决策）：
- 事实要求**参数级精确**——"T-90 速度"必须精确返回 60km/h，差一个数就错 → 用 SQLite 行存 + 属性过滤（ChatDB 符号记忆思想）
- 经验要求**语义召回**——"夜战吃过亏"和"夜间突袭遭伏击"字面不同但语义相同 → 用向量库（ExpeL 思想）
- **单一存储无法同时满足两种要求**，这不是过度设计，是任务性质决定的

## 1.5 字段级放置蓝图：进了容器放在哪（对齐代码）

> 1.4 回答"**信息归哪类**"，本节回答"**进了容器放哪个字段**"——把 `schema.py` / `working_memory.py` / 双库 / `boundary.py` 的放置规则一次讲清，被追问"具体怎么存"时直接翻本节。

### 1.5.1 短期容器 `WorkingMemorySlot`：一场一槽，11 字段各司其职

组织范式 = MemGPT 分层（`working_context` 常驻 + `fifo_queue` 滚动）；**一个规划场次绑定一个槽位**：

| 字段 | 放什么 | 压缩待遇 |
|---|---|---|
| `goal` / `constraints` | 本次规划目标、作战约束 | 🔒 **永不被删**（约束被压缩破坏 = 规划出错） |
| `working_context` | 高频关键信息常驻区 | 最后才动它 |
| `fifo_queue` | 消息/战报滚动队列（最旧先出） | **主要压缩对象** |
| `query_list` | ② 检索计划（`QueryItem{intent, target, route, query_text, answer_memory_ids}`，命中回填） | 不压缩——它是审计对象 |
| `loaded_memory` | ④ 已装载长期记忆 id 登记（溯源 + 消融统计） | — |
| `intermediate_results` | 管线中间结果（分析/生成/比较各步产物） | — |
| `plan_id` / `status` / 时间戳 | 场次身份与生命周期（`open/closed`，`touch()` 统一刷新） | — |

**容量与换页**（`working_memory.py`）：`capacity_tokens=4000`（简化计量：1 中文字≈1 token）→ **70% 预警** `memory_pressure=True`（SCM 式，上层可提前归档）→ **100% flush**：驱逐最旧 ~50% → "旧递归摘要 + 被驱逐消息"→ 新摘要（≤120 词）→ 存 `archived` **不丢**，`close_session()` 时并入复盘材料（即 2.2 节第三个改造）。

**渲染顺序**（`render()`）：头部 目标/约束 → 历史摘要 → 关键信息 → 查询列表 → 尾部 最近 20 条消息——关键信息永远在**首尾**（LongLLMLingua 位置偏置结论）。

**压缩三档**（`compression.py` 策略类 + `get_strategy(name)` 工厂，G1 消融一行切换）：`truncate`（截断·MVP 零依赖）→ `summarize`（LLM 摘要）→ `llmlingua`（删 token 式压缩，延迟导入适配器已预留）。

### 1.5.2 长期容器 `MemoryEntry`：13 字段统一条目，进哪个库看类型

双库共用同一数据模型（`schema.py` 单一事实源），字段按用途分四组：

| 字段组 | 字段 | 服务什么 |
|---|---|---|
| 本体（3） | `id`（形如 `fact-1a2b3c4d`）/ `type` / `content` | 条目识别与正文 |
| 溯源（3） | `source` / `session_id` / `timestamp` | 创新点 E：每条注入规划的记忆可回查来历 |
| 遗忘模型（4） | `importance`（S 初值 + 保护线判据）/ `decay_strength`（S，召回 +1）/ `recall_count` / `last_recalled_at`（t 起点） | MemoryBank 艾宾浩斯 `R=e^(-t/S)` 先快后慢；`mark_recalled()` 实现"间隔效应" |
| 进化回放（3） | `merged_from` / `op_history` / `metadata` | G4 消融可重演"记忆怎么来的"；`metadata` 承载事实库属性键值 |

**双库形态差异**（同一接口 `BaseLongTermStore`，读/写方法分两段——"检索只读、进化只写"的接口化）：

| 维度 | 事实库 `FactualStore` | 经验库 `ExperientialStore` |
|---|---|---|
| 存储 | SQLite 单文件行存（12 列，`attrs_json` 属性键值） | 内存 dict + 向量索引（接口留 FAISS 持久化位） |
| 检索主路 | `search_attrs()` 属性精确过滤（**参数级**，ChatDB 符号查询 MVP） | 向量语义召回（编码 = 正文 + source，带情境） |
| 打分 | 向量 cosine 主 + 关键词 LIKE 兜底（命中记 1.0） | `0.8×cosine + 0.2×min(importance/3, 1)`——重要教训更易浮出（Reflexion：失败学得最多） |
| 命中强化 | `persist_recall()` 回写 SQLite（防重启丢失） | 内存即时生效（方法保留仅为接口对称） |
| 论文依据 | ChatDB（数据库即符号记忆） | ExpeL（轨迹召回）+ Reflexion（语言经验） |

> **强化统一时点**：`mark_recalled()`（S+1、t 重置）只在三路融合排序后执行**一次**——否则三路互检会让同一记忆 `recall_count` 虚涨 3 倍、艾宾浩斯模型失真（4.2 节 B2 修复）。

### 1.5.3 放置判定表 + 双向禁止（`boundary.py`——"表即文档"）

1.4 的分类学在代码里落成**六行判定表** `CONTENT_RULES`（新增内容类别只需加一行；两把尺子的取值由表带出）：

| 内容类别 | 归属层 | 尺子A·来源 | 尺子B·时间 |
|---|---|---|---|
| `goal`（本场规划目标） | 短期 only | 任务内 | 场次生命周期 |
| `constraint`（本场作战约束） | 短期 only | 任务内 | 场次生命周期 |
| `message`（场次消息/中间结果） | 短期 only | 任务内 | 场次生命周期 |
| `fact_param`（装备参数/条令条款） | 长期·事实 | 跨任务 | 持久 |
| `fact_event`（战例客观经过） | 长期·事实 | 跨任务 | 持久 |
| `experience`（成败教训/可复用对策） | 长期·经验 | 跨任务 | 持久 |

**双向禁止**（边界的强制力，不靠自觉）：
- **短期 → 长期**：场中直写长期一律被 `check_write()` 拒绝；唯一合法通道是复盘晋升 `promote()`（G1–G3 门控，见 1.3）；
- **长期 → 短期**：只能以检索结果形态进入（`retrieve → load_memory` 登记），`validate_load()` 拦"整段拷进 FIFO"——"检索只读、进化只写"的解耦不被绕过。

**晋升模板关键词**（G2 的 Mock 实现 `PROMOTION_PATTERNS`；接真模型换 LLM 分类，接口不变）：
- 事实：参数 / 条令 / 海拔 / 编制 / 性能 / 射程 / 速度 / 态势 / 部署
- 经验：教训 / 经验 / 对策 / 失败 / 成功 / 复盘 / 下次 / 应当 / 避免

### 1.5.4 与讲义"三类记忆内容"的对应（docs/03 §16.2 / §18.1）

| 讲义分类（代表工作） | 我们的落位 |
|---|---|
| ① 同一任务内的历史交互（Generative Agent / MemoChat / TiM / Voyager） | 短期槽位全部字段 + flush 归档（并入复盘材料） |
| ② 跨任务的经验（Reflexion / Synapse / ExpeL） | 经验库——复盘晋升写入，跨场次语义召回 |
| ③ 外部知识（ReAct / GITM） | 事实库——知识库导入，受智戎**知识锚定**约束（库外经验不许混入） |

讲义 18.1"短期→长期转换用**反思与抽象**" → 我们的复盘驱动晋升（G1）+ `abstract()` 教训抽象（2.4 节四操作）。

# 第二部分：思考路径——每个设计为什么这样定

## 2.1 总体架构：为什么是"七步闭环"

**问题**：讲义给的是"记忆形成/检索/进化"三段式，太抽象，无法直接开发。

**我们的推导**：把三段式按**时间轴展开**成可执行的闭环——

```
①规划（建槽位·定目标约束）→ ②查询列表（显式化"我需要什么"）
→ ③检索（三路混合）→ ④装载（短期记忆组装上下文）
→ ⑤规划输出 → ⑥AFSIM 推演反馈 → ⑦记忆进化（复盘沉淀）
                    ↑___________________________|
```

**为什么查询列表要显式化**（创新点 C 的由来）：观察到 LLM 直接检索时"查什么"是隐式的、不可控的。我们让规划阶段先产出结构化查询列表（`QueryItem{intent, target, route, query_text}`），检索按列表执行、命中结果回填——**检索计划先于检索执行，事后可审计**。这借鉴了 ChatDB 的 Chain-of-Memory。

**为什么是闭环而非流水线**：第 ⑦ 步的产物（新经验）会改变第 ③ 步的输入（下场次检索命中）——demo 中 P002 场次召回的正是 P001 复盘写入的教训（`source: '复盘:P001'` 可溯源）。这个自增强回路就是"越用越强"的机制保证。

## 2.2 短期记忆：为什么选 MemGPT 范式 + 三个本地化改造

**选型推理**：候选有三种——滑动窗口（太简单，丢约束风险）、摘要压缩（丢细节）、MemGPT 分层（working context 常驻 + FIFO 滚动 + 阈值归档）。选 MemGPT 因为它**天然区分"关键信息常驻"与"历史消息滚动"**，正好映射作战场景的"约束不可丢"与"战报可压缩"。

**但我们做了三个关键改造**（每处都有代码注释标注）：

| MemGPT 原设计 | 我们的改造 | 为什么改 |
|---|---|---|
| LLM 自主决定换页（函数调用） | **确定性阈值**（70% 预警 / 100% flush） | 消融实验要求可复现；LLM 换页不可测试 |
| 分页决策靠系统提示引导 | 阈值化为 `memory_pressure` 只读属性 | 一行断言即可测试 |
| flush 出的消息进 recall storage 即止 | **归档并入复盘材料**（缝合 MemGPT 与 TiM 的缝） | 否则被压缩的信息永远失去晋升机会 |

第三个改造是我们在读两个论文源码时发现的"缝合缺口"：MemGPT 只管压缩不管沉淀，TiM 只管复盘不管压缩——中间被压缩掉的信息成了孤岛。`close_session()` 里把 `archived` 拼进复盘材料，一行代码补上这条缝。

## 2.3 检索：为什么三路都要

**问题分解**：作战查询天然分三类，各有所长——

| 查询类型 | 例子 | 最优路径 | 为什么 |
|---|---|---|---|
| 语义相似 | "夜战教训" | vector | "夜战吃亏"≠字面重叠，需语义泛化 |
| 型号代号 | "T-90" | bm25 | 向量对专有名词反而不稳，字面最准 |
| 参数精确 | "红方坦克破甲厚度" | sql | 需要确定性答案，向量给不出"参数级" |

**融合方案**：三路各自归一化（cosine→[0,1]、BM25→max 归一、SQL 恒 1.0）后加权求和，权重 α/β/γ 是消融 G5 的扫描点。**外加 min_score 阈值**（借鉴 ExpeL/Mem-α/MemP 三家源码都有的细节）：低分结果不返回——噪声进上下文比漏召回更伤。

## 2.4 进化：四操作的建议-执行分离

**核心设计原则**（docs/09 决策 2）：**LLM 只建议，代码执行**。

```
复盘文本 → LLM 抽取建议 [{op:write, type:experience, content:...}]   ← 建议侧（可换真模型/RL）
        → 代码执行：查重门控 → 写入 → 相邻合并 → 遗忘扫描 → 教训抽象   ← 执行侧（确定性、可回放）
```

**为什么分离**：作战复盘必须可审计——"为什么删了这条记忆？谁决定的？"全 LLM 黑盒无法回答。分离后每次进化产出 `EvolutionReport`（四操作计数 + 拒绝原因），消融实验直接统计此对象。

**四操作各自的论文依据与本地化**：

| 操作 | 论文来源 | 我们的改造 |
|---|---|---|
| 写入 | PREMem 链接对 θ | θ=0.80（MockEmbedding 分布偏高；接真模型回调 0.6，注释写明） |
| 合并 | TiM merge / Memp Add⊖Del⊕Update | `merged_from` 记录来源，可回放 |
| 遗忘 | MemoryBank R=e^(-t/S) | **加"失败教训保护线"**（importance≥2 永不遗忘）——论文没有，来自"作战失败不能忘"的领域常识 |
| 抽象 | TiM Post-thinking / StructMem 周期整合 | 本场新经验 ≥2 条触发（替代事件计数启发式） |

# 第三部分：实现路径与耦合方式

## 3.1 分层解耦——模块如何协作

```
┌─ pipeline.py ──── 七步编排（只管流程顺序，不含业务逻辑）
├─ controller.py ── 总调度（唯一同时碰四模块的角色；SCM 思想）
├─ boundary.py ──── 三道门控 + 审计（跨切面，被 evolution 调用）
├──────────────────────────────────────────────
│  short_term/  working_memory + 压缩策略        │ 四大能力模块：
│  long_term/   factual(SQLite) + experiential(向量) │ 互相不 import 对方，
│  retrieval/   bm25 + hybrid(三路融合)          │ 只通过 schema 数据对象交互
│  evolution/   四操作 + 复盘驱动入口             │
├──────────────────────────────────────────────
│  schema.py ──── 统一数据模型（单一事实源）        │
│  llm.py / embeddings.py ── 外部能力抽象          │
│      （MockLLM/MockEmbedding 离线可跑；OpenAI 兼容骨架随时切换）
└──────────────────────────────────────────────
```

**耦合规则**（写在 `long_term/base.py` 接口注释里）：
1. **检索只读、进化只写**——独立评测互不污染
2. 依赖注入：`MemoryController(llm=?, embedding=?, ...)` 全可替换——Mock 与真模型**业务代码零改动**
3. 数据模型改动只从 `schema.py` 出发——单一事实源
