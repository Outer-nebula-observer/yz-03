# 智戎场景适配：流水线场次范式 vs 真实平台差异——问题分析与解决方案

> 一句话问题：你的记忆系统从设计到验证都假设"场次 = 一次完整任务 = goal→查询→检索→规划→反馈→复盘→进化"的流水线；智戎真实运行可能并不完全这样。下面逐条列出可能出现的效果问题，并给出可落地的适配方案。

---

## 一、可能的问题（按风险从高到低）

### P1. 没有明确的"场次结束/复盘"时机
- 现状：进化只在 `close_session(review)` 触发，依赖"复盘文本"。
- 智戎可能的真实情况：
  - 任务是连续作战，没有一次性的"结束"信号；
  - 复盘不是人工文本，而是系统自动评估（成功率/伤亡/耗时等数值）；
  - 一场任务中目标会中途变化（Plan 变更）。
- 后果：记忆长期不进化 → "越用越强"失效；或复盘文本缺失 → 抽取为空，进化退化。

### P2. 规划阶段与 MDMP 七阶段不一致
- 现状：查询按 MDMP 七阶段模板生成，阶段亲和 + 阶段归因都依赖这套阶段。
- 智戎可能的真实情况：
  - 只做部分阶段（跳过了方案比较/命令拟制）；
  - 阶段顺序/粒度不同（例如"态势感知→计划生成→执行"三步式）；
  - 任务解读不由 LLM 走完整流程，而是由系统固定流程。
- 后果：阶段模板生成无关查询、阶段亲和乱加、归因标签失真 → 检索噪声上升。

### P3. 目标/约束/查询的输入形态不同
- 现状：`goal` 是自然语言一句话，`constraints` 是字符串列表，`queries` 是手写 QueryItem。
- 智戎可能的真实情况：
  - 任务描述是结构化 JSON（敌情、地形、兵力编成分别给）；
  - 没有"约束列表"概念，而是规则引擎/数据字段；
  - 查询由智戎其它模块产生，或不产生显式查询。
- 后果：query_list 生成可能错位；约束不压缩保护失去意义；检索计划显式化（创新点 C）落空。

### P4. 反馈信号不是"复盘文本"
- 现状：`hook_feedback(text)` 期望一段包含"教训/经验/参数/条令"的自然语言文本。
- 智戎可能的真实情况：
  - AFSIM 输出结构化结果：成功/失败布尔 + 数值 + 事件日志；
  - 推演次数多但每场很短，复盘成本高。
- 后果：抽取不出教训 → 经验库无增长；或把机械日志误当教训写入（污染）。

### P5. 领域/词汇分布与测试集差异大
- 现状：测试集与消融都在假想战场（2号高地、夜战）上用 Mock 词袋跑过。
- 智戎真实数据：
  - 装备/条令/战例用词、粒度、命名与虚构数据集差异大；
  - 真实知识库条目可能非常长、结构化程度高。
- 后果：min_score/θ/艾宾浩斯阈值需要重标定；语义检索在真实词表上表现未知；C 类转述命中可能仍弱。

### P6. 场次标识/生命周期不匹配
- 现状：`plan_id`、`session_id`、`source="复盘:P001"` 这些字符串被用于"复用检测"。
- 智戎可能的真实情况：
  - 任务 ID 是数据库 UUID/长串；
  - 一场"规划会话"被拆成多个执行片段；
  - 多席位并行跑同一个任务（共享 or 隔离记忆未定义）。
- 后果：复用检测失效（source 前缀不对）；多席位向同一个 记忆库并发写入 → 重复/冲突。

### P7. 时延与实时性约束
- 现状：检索本地快；但真模型（DeepSeek）单次生成规划约 25s，抽取约 2s。
- 智戎可能的真实情况：要求 30 秒内出方案，或在推演过程中频繁检索。
- 后果：规划生成路径已达标（本地检索快），但若每次规划都走真 LLM 生成 + 真 embedding 建库，可能超预算。

### P8. 知识锚定缺口
- 现状：长期记忆入库前没有与权威知识库比对（docs/04 承诺未实现）。
- 智戎真实要求："知识锚定——只许用库里的数据"。
- 后果：复盘抽取的"经验/参数"可能来自**库外**，直接违反平台约束；答辩会被追问。

---

## 二、解决方案（按实施顺序）

### S1. 把"场次"抽象成事件驱动（先做，解决 P1/P6）
- 不把"一次进化"绑死在"一次结束"上，改造成**状态机/事件钩子**：
  - `on_session_start(pid, goal, constraints, meta)`
  - `on_feedback(kind, payload)`（kind 支持 text/json/numeric）
  - `on_evolve(reason="session_end|periodic|critical", review_text=None, review_obj=None)`
- 智戎侧可以随时调用 `hook_feedback` 累积，再由 `hook_close` 或一个 `hook_evolve` 手动触发；没有结束信号时，按策略（每 N 次反馈/定时/任务切换）触发进化。
- 实现：扩展 `integration/zhirong_kit/adapter.py` 增加 `hook_evolve(reason, review_or_payload)` 和 `hook_append_feedback(fragment)`。

### S2. 阶段集可配置（解决 P2）
- 把 `stages.py` 的 MDMP 七阶段改成**注册表 + 配置**：
  - `configure_stages(custom_stages)` 允许智戎传入自己的阶段列表/模板；
  - 阶段查询模板缺失时，回退到"LLM 从任务文本生成查询"（query_by_llm），不再强依赖阶段。
- 阶段归因也做成可替换：`attr_stage` 从关键词模板升级为 LLM 归因，或由智戎显式传入"当前阶段"。

### S3. 输入规范化适配器（解决 P3）
- 在 `zhirong_kit` 增加 `normalize_task(task_json)`：
  - 把智戎的结构化任务 JSON 映射为 `goal + constraints + query_list`；
  - 若智戎自带查询，则原样通过；否则用阶段模板/LLM 生成；
  - constraints 从"规则数组"映射为字符串列表（供不可压缩保护）。
- 让"手写 QueryItem"不再是唯一输入，支持"任务对象 → 查询计划"的转换。

### S4. 反馈多模态化（解决 P4）
- `hook_feedback` 支持：
  - `text`：沿用现状；
  - `structured`：接收 `{result:"success|fail", metrics:{...}, events:[...]}`；
  - 由适配器用模板或 LLM 把结构化结果转成复盘文本（`review_builder`）；
- 增加"教训抽取置信度"：对机械日志做关键词/规则过滤，避免把过程日志当教训。

### S5. 领域迁移标定（解决 P5）
- 接入真实数据后必须重跑：
  - `python -m eval.ablation`（真模型嵌入下）重标定 `min_score`、`θ`；
  - 用智戎真实知识库抽样 20~50 条做命中率/词表覆盖检查；
  - 对 C 类转述查询做专项测试，确认真向量下语义泛化成立；
- 建立"适配巡检脚本"：`zhirong_kit/domain_check.py`，输入真实样本，输出检索命中/阈值建议/风险表。

### S6. 持久化与会话隔离（解决 P6）
- 记忆库按 `scope` 分层：
  - 全局库（跨任务通用知识）；
  - 任务类库（按 `task_type` 分区）；
  - 席位数库（多席位隔离，按 `seat_id` 过滤）。
- `session_id` 使用智戎任务 ID；复用检测从 `source.startswith("复盘:")` 改为元数据字段 `memory.source_type="review"`，不再依赖字符串前缀。
- 并发写入用现有 RLock 串行化即可，但要处理"同任务多席位"的读写一致性。

### S7. 时延与链路优化（解决 P7）
- 检索全部走本地（已达标）；
- 真 LLM 生成规划若超预算：提供 `plan_mode="fast"`（先用 Mock/模板，再用真模型做润色），或缓存常用查询；
- 建库用批量 embedding + 缓存（已有缓存），避免每场重嵌入大量知识；
- 记录 per-hook 时延到 `IntegrationLog`，超阈自动降级。

### S8. 知识锚定校验（解决 P8，答辩必答）
- 在 `MemoryEvolution.write` 前增加 `KnowledgeAnchor.validate(content)`：
  - 对接智戎知识库（如通过 SDK 检索服务查实体/参数）；
  - 命中才入库；未命中进入"待人工确认"区而非直接写入；
  - 与现有 `boundary.promote` 串联成第四道门（G4 锚定门）。
- 短期若没拿到知识库接口：先把"锚定状态"记在 metadata（`anchored=false`），对未锚定经验降低检索权重或标记，避免违背"只许用库内数据"。

## 二·五、P0 落地状态（v0.8 已实现）

S1（事件驱动进化）、S3（任务规范化）、S4（结构化反馈）已在
`integration/zhirong_kit/` 实现并验证：
- `ZhirongEventAdapter`：`hook_evolve` / `hook_append_feedback` / `hook_feedback(structured)`
- `normalize_task(task_json)`：中文/英文别名自动映射
- HTTP 桥新增 `/hook/evolve`、`/hook/normalize`、`/hook/append_feedback`、`/hook/plan(task)`
- `domain_check.py`：领域巡检 + min_score 建议（接入真实数据后运行）
- selfcheck 扩至 5 项全过（含 normalize / 结构化反馈→事件驱动进化）

仍待落地：S2 阶段注册表、S5 真实数据正式重标定（工具已就绪，等数据）、
S6 scope 分区、S8 知识锚定（可先用 metadata 标记）。

## 三、落地建议（优先级）

| 优先级 | 动作 | 对应问题 |
|---|---|---|
| P0 | 扩展 `zhirong_kit`：`hook_evolve` + `hook_feedback(structured)` + `normalize_task` | P1/P3/P4 |
| P0 | 接入真实数据后重标定 min_score/θ + 领域巡检 | P5 |
| P1 | 阶段注册表 + LLM 查询回退 | P2 |
| P1 | 记忆库按 scope 分区 + 元数据复用检测 | P6 |
| P1 | 知识锚定校验（至少 metadata 标记） | P8 |
| P2 | 真模型时延模式、批量 embedding、并发策略 | P7 |

## 四、结论

你的"流水线场次"不是设计错误，它是**一个清晰、可测的基准范式**——没有这个范式就没法做消融。但接入智戎时不能把它当"唯一范式"硬套，而是要把它变成**默认实现**，在 `zhirong_kit` 适配层把智戎的真实时序/输入/反馈翻译成本系统能处理的事件。只要 P0 四件事（事件驱动进化、结构化反馈、任务规范化、领域标定）先落地，场景差异带来的效果问题就基本可控；剩余问题（锚定、并发、时延）有明确技术路线，不会改变系统内核。
