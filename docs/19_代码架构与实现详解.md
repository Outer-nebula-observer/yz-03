## 1. 架构总览与模块联系

### 1.1 分层

```
┌────────────────────────────────────────────────────────────┐
│ 入口/演示   pipeline.py  examples/*  webui/  zhirong_kit/   │
├────────────────────────────────────────────────────────────┤
│ 编排       controller.py（总调度，唯一同时碰四模块）           │
├────────────────────────────────────────────────────────────┤
│ 跨切面     boundary.py（边界门控）· stages.py（MDMP 阶段）    │
├────────────────────────────────────────────────────────────┤
│ 能力层     short_term/  long_term/  retrieval/  evolution/   │
├────────────────────────────────────────────────────────────┤
│ 模型层     schema.py（唯一数据模型）                          │
│ 外部抽象   llm.py / embeddings.py（Mock ↔ 真模型）            │
└────────────────────────────────────────────────────────────┘
```

### 1.2 模块之间“谁调用谁”（调用链）

- **schema.py 被所有模块依赖**：`MemoryEntry`、`QueryItem`、`RetrievedMemory` 是四能力层之间传递数据的唯一“信封”。
- **四个能力层互相不 import**：`short_term` 不 import `retrieval`，`retrieval` 不 import `evolution`。它们只通过 controller 或 schema 对象间接协作。这是“可独立消融”的物理基础。
- **controller.py 是粘合剂**：
  - 启动场次 → 创建 `WorkingMemory`（短期）
  - 检索 → 调 `HybridRetriever.retrieve` → 把结果 `load_memory(id, brief)` 进短期
  - 收场 → 把复盘文本交给 `MemoryEvolution.evolve_from_review`（长期写入）
- **evolution 调 boundary**：写入前 `boundary.promote()` 做门控；写入 `factual/experiential` 存储。
- **retrieval 调 long_term**：`HybridRetriever` 直接持有两个 store 的引用，只读。
- **llm/embeddings 被 controller / evolution / pipeline 注入**，通过接口（Protocol / duck type）替换 Mock↔真模型。

### 1.3 一次完整请求的数据流（以“开一场规划”为例）

```
pipeline.run_session / controller.start_session
  └─ 建 WorkingMemorySlot（goal/constraints/query_list）
  └─ retrieve_and_load
       └─ HybridRetriever.retrieve(query)
            ├─ _route("vector")  → FactualStore.search_vector / ExperientialStore.search
            ├─ _route("bm25")    → BM25.score_topk
            ├─ _route("sql")     → FactualStore.search_attrs / search_content_like
            ├─ _norm()           → 各路分数归一化
            ├─ 融合（按 entry.id 加权累加）
            ├─ 阶段亲和/时间衰减 → min_score 过滤 → top_k
            └─ mark_recalled + persist_recall（强化落库）
       └─ controller 把命中的 brief 写入 wm.slot.loaded_briefs
  └─ 规划输出（llm.chat；Mock 回显 / DeepSeek 生成）
  └─ close_session(review)
       └─ MemoryEvolution.evolve_from_review
            ├─ llm.extract_memory_ops → 候选写入建议
            ├─ boundary.promote → 门控
            ├─ self.write  → θ 查重 → store.add
            ├─ 新条目合并去重
            ├─ forget() → 遗忘 + 墓碑
            └─ abstract() → 抽象成通用教训
```

## 2. 关键实现逐行精讲

> 下面选的是“你知道它做什么、但不一定知道它怎么写”的函数。每个代码块都带逐行注释。

### 2.1 遗忘模型：`schema.py::MemoryEntry.retention`

```python
def retention(self, now=None):
    # R = e^(-t/S)，艾宾浩斯留存率
    now = now if now is not None else time.time()
    # t = 距上次召回（或创建）的天数；除以 86400 把秒换成天
    t = (now - (self.last_recalled_at or self.timestamp)) / 86400.0
    t = max(t, 0.0)                                        # 时间倒退当 0 防御
    import math
    return math.exp(-t / max(self.decay_strength, 1e-6))   # S 作分母，S 越大衰减越慢
```

实现要点：
- `last_recalled_at` 比 `timestamp` 优先：命中后 t 从最近一次使用重新计时；
- `S=decay_strength` 是“强度”，每次 `mark_recalled()` 会 `S+=1` 且 `t` 清零；
- 返回值 ∈ (0,1]；`forget()` 的阈值是 0.3，等价于“若不再被使用，约 1.2 天×S 后进入遗忘线”。

### 2.2 混合检索：`hybrid.py::retrieve`（最复杂的一段）

```python
# 1) 收集主路 + 另两路结果
primary = self._route(q, top_k)             # 按 q.route 走主路
others = []                                  # 其余两路“补充计分”
if mode == "hybrid":
    for alt in ("vector", "bm25", "sql"):
        if alt != q.route:                   # 不重复主路
            qq = QueryItem(..., route=alt, ...)
            others.extend(self._route(qq, top_k))

pool = primary + others
# 2) 每一路分数统一到 [0,1]
for r in pool:
    r.score = self._norm(r.route, r.score, pool, q.query_text or q.intent)
    # vector：(cos+1)/2  → 这里 v0.3 改为 max(cos,0)
    # bm25：  s / self_score(query)          → 防单字巧合被放大
    # sql：   恒 1.0（属性精确命中=强信号）

# 3) 按 entry.id 聚合多路得分（同一条可能被多路命中）
fused = {}
for r in pool:
    w = weights.get(r.route, 0.1)            # hybrid 用 α/β/γ；single 用 1.0
    fused.setdefault(r.entry.id, {"r": r, "s": 0.0, "routes": []})
    fused[r.entry.id]["s"] += w * r.score    # 加权累加（融合分）
    fused[r.entry.id]["routes"].append(r.route)

# 4) 阶段亲和：查询带 stage 且记忆 metadata.stage 对口 → 加 stage_bonus
#    （在 min_score 之前加，让对口弱记忆也能过阈值）
if getattr(q, "stage", ""):
    for item in fused.values():
        if item["r"].entry.metadata.get("stage") == q.stage:
            item["s"] += self.stage_bonus

# 5) 时间敏感检索（默认关闭）：S 越大/越新，越少降权
if self.time_decay_weight > 0:
    for item in fused.values():
        item["s"] *= 1.0 - w * (1.0 - item["r"].entry.retention(now))

# 6) 阈值过滤 + 排序 + top_k
ranked = sorted(fused.values(), key=lambda x: x["s"], reverse=True)
ranked = [item for item in ranked if item["s"] >= self.min_score][:top_k]
# 注意：attrs 精确命中（exact_ids）会绕过 min_score——符号路是“构造性相关”

# 7) 对最终结果统一执行一次命中强化（mark_recalled+1、S+1）并落库
for i, item in enumerate(ranked):
    r = item["r"]
    r.score = item["s"]; r.rank = i + 1
    r.entry.mark_recalled()
    store.persist_recall(r.entry)            # SQLite 事实库需要落库
```

**为什么这样能实现“任务感知检索”**：查询携带 target/route/attrs/stage，路由把“查什么类型的记忆、走哪条路、有没有精确条件、属于哪个阶段”都编码进 QueryItem，检索完全由这个对象驱动。

### 2.4 写入查重：`memory_evolution.py::write`

```python
def write(self, type_, content, ...):
    store = self.factual if type_ == MemoryType.FACT else self.experiential
    new_vec = self.vindex.model.embed(content)   # 新内容向量（只算一次）
    dup = None; best_sim = -1.0
    for cid in store.candidates():               # 遍历同库全部现有条目
        existing = store.get(cid)
        if existing is None: continue
        # 优先读 add() 时已缓存的向量，避免重复 embed（性能修复）
        cand_vec = (store.vindex._vectors[cid]
                    if cid in store.vindex
                    else store.vindex.model.embed(existing.content))
        sim = cosine(new_vec, cand_vec)
        if sim > best_sim:                       # 记住最像的那个
            best_sim, dup = sim, existing
    if dup is not None and best_sim > self.merge_theta:
        return None                              # 与现存太像 → 判重复，返回 None（调用方记 skip）
    entry = new_entry(type_, content, ...)       # 否则真的入库
    store.add(entry)
    return entry.id
```

**为什么不直接 SQL “去重”**：这是语义去重，靠向量余弦，而不是字符串相等。

### 2.6 工作记忆：`working_memory.py::_flush` 与 `render`

```python
def _flush(self, keep_ratio=0.5):
    n = len(self.slot.fifo_queue)
    if n <= 2: return
    cut = max(1, int(n * keep_ratio))          # 驱逐前 ~50%
    evicted = self.slot.fifo_queue[:cut]        # 取出最旧
    self.slot.fifo_queue = self.slot.fifo_queue[cut:]
    material = (self._recursive_summary + "\n" + "\n".join(evicted)).strip()
    self._recursive_summary = self.llm.summarize(material, max_words=120)
    self.archived.append({"evicted": evicted, "summary": self._recursive_summary})

def render(self):
    # 顺序刻意：目标/约束（首部不可压缩）→ 装载记忆 → 查询列表 → 最近消息（尾部）
    # 依据 LongLLMLingua 位置偏置：关键信息放首尾
    parts = []
    if self.slot.current_stage: parts.append(f"【规划阶段】{...}")
    if self.slot.goal: parts.append(f"【目标】{...}")
    if self.slot.constraints: parts.append("【约束】" + ...)
    if self.slot.loaded_briefs:
        parts.append("【装载记忆】\n" + "\n".join(...))   # 检索结果真正进 prompt
    if self._recursive_summary: parts.append(f"【历史摘要】{...}")
    if self.slot.query_list: parts.append("【查询列表】" + ...)
    if self.slot.fifo_queue: parts.append("【近期消息】" + ...)
    return "\n".join(parts)
```

## 4. 当前问题与不足（架构逻辑层面）

### 4.1 架构逻辑不足

| # | 不足 | 原因 | 影响 |
|---|---|---|---|
| 1 | **遗忘是“硬删除”** | `Forget()` 直接 remove，只留墓碑日志 | 无法回滚/恢复；若误删重要经验不可逆（墓碑仅审计） |
| 2 | **经验冲突无仲裁** | 两条矛盾教训可共存，谁分高谁被召回 | 新经验不一定覆盖旧经验，规划可能被过时经验误导 |
| 3 | **importance 静态** | 写入时由 LLM/规则给，之后不变 | 没有“这条经验实际好不好用”的反馈校准 |
| 4 | **知识锚定未实现** | 入库前没有和权威知识库比对 | 违反 docs/04 §1.2 承诺，防编造防线缺一角 |
| 5 | **合并/抽象触发是启发式** | 相邻成对比较、≥2 条才抽象 | 可能漏合并/误抽象 |
| 6 | **WebUI 数据全在前端逻辑** | 前端直接调一堆 /api，无状态管理 | 代码规模大了之后可维护性变差 |
| 7 | **Mock 与真模型的检索口径不同** | Mock 词袋 vs 真向量分布差异大 | min_score/θ 需要按 embedding 重标定，不能一个默认值通吃 |

### 4.2 实现层面的已知问题（来自实验与评审）

- C 类转述命中在 Mock 下依赖单字判别（0.63），真语义需要真向量；
- G5 在 Mock 下 hybrid 不优于 vector 单路（p=0.626）——混合增益待真模型裁决；
- G4/G6 样本量小，p 值仅方向性；
- `forgotten_log` 无持久化（重启即失），若需要长期审计要落盘；
- 事件流 detail 目前不落盘（内存数组，最多 300 条）。

### 4.3 建议的下一步优先级

1. **真 embedding 消融重跑 + 重新标定 min_score/θ**（docs/13 §1.1/1.2）；
2. **动态信任分**：用 AFSIM 结果校准 importance（解决 #3，同时为冲突仲裁打基础）；
3. **遗忘改为延迟删除/软删除**：墓碑直接复用为软删状态，可恢复；
4. **知识锚定比对**（接智戎知识库后）。
5. WebUI 若继续变大，建议引入简单状态管理或后端聚合接口。
