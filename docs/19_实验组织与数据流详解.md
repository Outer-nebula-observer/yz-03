## 1. 一条用例如何变成指标：数据流

```text
eval/testset.py                       eval/ablation.py                eval/metrics.py
┌──────────────────────┐   build_stores   ┌─────────────────┐  retrieve  ┌─────────────────┐
│ SEED_FACTS           │ ───────────────► │ MemoryController │ ─────────► │ HybridRetriever  │
│ SEED_EXPS            │                  │ (each group 独立) │           │  hybrid/single   │
│ STAGE_PAIRS          │                  └─────────────────┘           └────────┬────────┘
└──────────────────────┘                                                        │ ranked ids
     RETRIEVAL_CASES ──► [{qid, category, query, gold, distractor}]             ▼
     CROSS_SESSION_CASES ──► [{qid, s1_goal, s1_review, s2_query, expect_keyword}] ┌─────────────┐
                                                                                │ evaluate_retrieval │
                                                                                │ hit/recall/mrr/ndcg │
                                                                                └─────────────┬─────┘
                                                                                                │ per-case dict
                                                                                                ▼
                                                                                  eval/stats.py
                                                                                  bootstrap CI / 置换检验 / 随机基线
                                                                                                ▼
                                                                                  print_report + ablation_report.json
```

关键点：

1. **确定性 id**：`build_stores` 给每条种子记忆一个 `sha1(内容)` 的 id，所以 44 条用例的 gold 在**任何一组控制器里都指向同一个 id**。这是“固定用例集 + 跨组对比”能成立的代码基础（没有它，每组建库的 uuid 不同，gold 无法复用）。
2. **每次检索都用新的 QueryItem**：`run_retrieval` 里复制 `QueryItem(q.q_id, q.intent, q.target, route, query_text, attrs, stage)`，避免 `retrieve()` 的回填/强化副作用污染下一次。
3. **指标只看排名**：`retrieve` 返回的 `hits` 只取 `entry.id` 列表，交给 `evaluate_retrieval`；分数本身不进指标，排序才进指标。
4. **每个 case 产出一个小字典**：
   ```python
   {"qid": "a1", "category": "A", "mrr": 1.0, "hit@3": 1.0, "recall@3": 1.0,
    "ndcg@3": 1.0, "hit@5": ..., "recall@5": ..., "ndcg@5": ...,
    "gold_above_distractor": 1.0, "n_returned": 1}
   ```
   所有后续均值、分类别、显著性检验都吃这组 `per_case` 字典。

## 2. 消融 v2（G0–G6）的设计与代码

### 2.1 设计原理

消融要证明的是“**某层/某机制确实带来可测量的差异**”。这里用了四个手段：

- **固定用例集**：所有组跑同一批 44 条 A–G 用例。不允许“关了经验库就跳过经验类用例”——那会把“配置差异”和“用例集差异”混在一起。
- **依赖注入开关能力**：G2 的“仅事实库”不是改 case，而是 `_fresh(with_exps=False)` 往控制器里注入**空经验库**。经验类查询在 G2 下 gold 根本不在库里，自然 miss。
- **独立 controller**：每组 `_fresh()` 新建 `MemoryController`，避免上一组检索强化改了下一组的库状态。
- **统计检验**：先给随机基线和置信区间，再用配对置换检验给“差异显著”一个 p 值。

### 2.2 各组输入与开关

| 组 | 控制器构造 | 只读检索？ | 任务层？ | 代码位置 |
|---|---|---|---|---|
| G0 | `_fresh()` + 检索旁路 `_NullRetriever` | 否（空检索） | 是 | `run_all` G0 |
| G1 | 同 G0，但走完整会话流程 | 否 | 是 | G1 |
| G2 | `_fresh(with_exps=False, with_stage_pairs=False)` | 是，固定 44 条 | 是 | G2 |
| G3 | `_fresh()` 双库全开 | 是，固定 44 条 | 是 | G3 |
| G4 | 在 G3 库上先跑场次1复盘进化，再跑场次2查询 | 是（H 类 6 条） | 否 | `run_cross_session` |
| G5 | 同 G3，但 `route_override` 强制 vector/bm25/sql 单路 | 是（A/B/C/D/F） | 否 | G5 |
| G6 | 同 G3，`stage_bonus=0.15` vs `0.0` | 是（G 类） | 否 | G6 |

### 2.3 预计输出（JSON 结构）

顶层是 `report` 字典，落盘为 JSON：

```text
ablation_report.json
├── groups
│   ├── G0 / G1 / G2 / G3
│   │     ├── task: {constraint_sat, memory_citation, noise_pollution}
│   │     ├── retrieval: {hit@3, hit@5, recall@5, mrr, ndcg@5, gold_above_distractor, n_returned, _n}
│   │     └── by_category: {A: {...}, B: {...}, ...}
│   ├── G3_vs_G2: {paired_n, mean_diff_hit5, p_perm}
│   ├── G4: {summary, store_size}
│   ├── G4_control: {summary}
│   ├── G4_vs_control: {paired_n, p_perm}
│   ├── G5: {hybrid, vector, bm25, sql, hybrid(α...)}
│   ├── G5_hybrid_vs_vector: {paired_n, p_perm}
│   ├── G6: {on(0.15), off(0)}
│   └── G6_significance: {metric, paired_n, p_perm}
├── random_baseline
├── E_noise_study / F_forgetting_study / C_compression_study / S_sensitivity
├── task_layer_note
└── _meta: {testset, embedding, llm, elapsed_s, honesty}
```

### 2.4 参考指标与判读标准

检索侧统一 `ks=(3,5)`：

| 指标 | 含义 | 关键判读 |
|---|---|---|
| hit@k | top-k 是否含 gold | 单 gold 时的“有没有找对” |
| recall@k | top-k 覆盖 gold 比例 | 多 gold 时更细 |
| mrr | 第一个 gold 的排名倒数 | 排序“多快命中” |
| ndcg@k | 位置加权质量 | 多个 gold 是否都被排前 |
| gold_above_distractor | gold 是否排在干扰记忆前 | F/G 类专用，看“参数不张冠李戴”和“阶段亲和” |
| n_returned | 实际返回条数 | 负例应趋近 0；正常查询反映 min_score 滤除 |

任务层：

| 指标 | 含义 |
|---|---|
| constraint_sat | 约束判别词是否出现在规划输出 |
| memory_citation | 装载记忆核心片段是否出现在输出 |
| noise_pollution | 负例查询带入的记忆是否污染输出 |

### 2.5 如何验证（“这组数字有没有问题”）

按“结构关系”检查，不看绝对值：

1. `G2.by_category` 的 `C/D/G` 必须为 0——空经验库下经验类 gold 不存在，miss 是正确语义；出现 >0 说明注入失败。
2. `G3.retrieval.hit@5`（0.636）必须明显高于 `random_baseline`（0.357）；接近随机说明检索失效。
3. `G3_vs_G2.p_perm` 应 <0.05（实测 0.0001）。
4. `G4.summary.hit@5`（0.833）> `G4_control.summary.hit@5`（0），且负控 `false_cross_recall=0`。
5. `E_noise_study` 在 `min_score=0.16` 时负例返回率应为 0；>5% 就要重标定。
6. `F_forgetting_study` 必须是“删 10 / 保护 0 / 新写入 0，命中 0/5/5”；任何保护被删都算遗忘模型 bug。
7. G5 在 Mock 下 hybrid 不优于 vector 是**预期负结果**，不是 bug；看 `干扰压制` 是否 hybrid 更好。

## 3. 跨场次实验（H 类）

### 3.1 输入

`CROSS_SESSION_CASES()` 生成 6 条，每条含：

```python
{"qid": "h1",
 "s1_goal": "夜间夺占 2 号高地",
 "s1_review": "复盘：任务部分达成。教训：夜间突袭未前置电子压制…",
 "s2_goal": "夜间进攻 3 号高地",
 "s2_query": ("h1", "夜间进攻通信保障教训", "experience", "vector", "夜间 进攻 通信 干扰 教训"),
 "expect_keyword": "电子压制"}   # 用于运行期解析 gold
```

### 3.2 设计原理

- 处理组 `run_cross_session(with_evolution=True)`：先跑场次1（`start_session` + `close_session(s1_review)`，让进化真的写入）→ 场次2用 `s2_query` 检索 → gold 是“场次1 写入且含 expect_keyword”的条目（`resolve_cross_session_gold`）。
- 对照组 `with_evolution=False`：不跑场次1，gold 解析为空 → 必然 miss。
- 这样“进化写入对后续检索有用”被直接检验，而不是像旧版那样只看 store_size。
- h6 是负控：expect_keyword=None，gold=[]；检查“渡河教训是否混进巷战查询”（`false_cross_recall`）。

### 3.3 输出与读取

```json
"G4": {
  "summary": {"hit@3": 0.8333, "hit@5": 0.8333, "mrr": 0.8333,
              "from_s1_review": 0.8333, "false_cross_recall": 0, "_n": 6},
  "store_size": ...
}
"G4_control": {"summary": {"hit@5": 0, ...}}
"G4_vs_control": {"paired_n": 5, "p_perm": 0.0591}
```

读取要点：p=0.059 是样本太小导致的功效不足，不是没有效果；treat>0 且 control=0 本身就是正确方向的证据。

## 4. 任务层实验

### 4.1 输入

`run_task_group` 用 `TASK_MISSIONS`（3 个任务场次），每个任务是目标+约束+查询三件套，其中第三条查询是无关负例：

```python
{"goal": "夜间夺占 2 号高地",
 "constraints": ["禁止越境", "限时 4 小时", "优先保存装甲力量"],
 "queries": [("t1a", "查目标地形", "fact", "vector", "2号高地 地形…", None),
             ("t1b", "召回夜战教训", "experience", "vector", "夜间 行军 侦察 伏击", None),
             ("t1c", "无关查询", "fact", "vector", "电影 票房 统计", None)]}
```

### 4.2 设计原理

- G0 禁用检索（`_NullRetriever`），G1 同 G0 但走会话，G2/G3 开检索；
- 用 `ctl.render_context()` 拼上下文 → `llm.chat(...)` 生成规划 → `task_metrics.evaluate_task`。
- Mock 下 `memory_citation` 度量“上下文构造是否正确”；真模型下度量“LLM 是否善用记忆”。文档始终分开说。

### 4.3 输出

```json
"G0": {"task": {"constraint_sat": 1.0, "memory_citation": 0.0, "noise_pollution": 0.0}}
"G3": {"task": {"constraint_sat": 1.0, "memory_citation": 0.75, "noise_pollution": 0.0}}
```

## 5. 四个专项研究

### 5.1 E 噪声研究（min_score 标定）

- 输入：E 类负例 12 条 × min_score 网格 `(0.05, 0.10, 0.16, 0.25)`；
- 输出：每个阈值的“负例返回率 / 负例均返回条数 / 正例 hit@5”；
- 原理：阈值过低 → 负例漏进；过高 → 正例被滤。取“负例返回率降到 0 且正例不掉太多”的拐点（当前 0.16）。
- 读取：`E_noise_study["min_score=0.16"]`。

### 5.2 F 遗忘研究

- 三组合成数据：30 天未召回未保护（importance=1.5）×10、保护（2.0）×5、新写入 ×5；
- 跑 `evolution.forget()`，检查删除集合；
- 输出 `保护线行为` 和 `检索影响`（被删/保护/新记忆各 5 条查询的命中，应 0/5/5）；
- 另做 `强度S×时间扫描`：S=1/3/7 × 3天/10天/30天，看删除数——展示“召回次数（S）越多越难遗忘”。

### 5.3 C 压缩研究

- 构造 17 条放大消息灌入 `WorkingMemory`（capacity=300），分别用 truncate 和 summarize 压缩；
- 输出：峰值/压缩后 tokens、压缩率、约束保留、标记事实是否保留、归档次数；
- 注意：Mock 的 summarize 是截断式拼接，压缩率数字只在“链路正确”层面有意义，真模型后才谈“保真质量”。

### 5.4 S 敏感性扫描

- θ 扫描：近重复对与不同内容对在 θ=0.6/0.7/0.8/0.9 下的拦截/误拦；
- stage_bonus 扫描：0/0.05/0.15/0.30 下 G 类干扰压制；
- 读取：`S_sensitivity["θ=0.6"]`、`S_sensitivity["stage_bonus=0.15"]`。

## 6. 统计方法（eval/stats.py）原理

| 函数 | 原理 | 用途 |
|---|---|---|
| `random_hit_at_k(n,k,g)` | 解析式 `1-C(n-g,k)/C(n,k)` | 给 hit@k 一个“瞎猜下限” |
| `random_mrr(n,g)` | 单 gold 用 `H_n/n`，多 gold 蒙特卡洛 | MRR 随机基线 |
| `bootstrap_ci(xs)` | 有放回抽样 1 万次取均值分位数 | 均值的不确定性区间 |
| `paired_permutation_test(x,y)` | 逐对差值随机翻号，统计 | 两组是否显著不同 |

为什么用配对置换而不是 t 检验：hit@5 是 0/1 二值，不满足正态假设；G2/G3 的指标来自同一批 case 逐对配对，不能当独立样本。

## 7. 真模型验证（eval/verify_llm.py）

### 7.1 组织

| 项 | 输入 | 输出/判据 |
|---|---|---|

## 8. 冒烟测试的组织

`tests/test_smoke.py` 是零依赖的 assert 脚本，不用 pytest。21 个 `[PASS]` 对应 14 个函数。它测的是“每个模块的契约行为”而不是“效果”。例如：

- `test_pipeline` 断言第二场真的召回 `source='复盘:P001'`（跨场次复用）；
- `test_review_fixes` 的 9 项回归锁定评审修复（上下文注入/单路/句级抽取/持久化等）。

运行：`python tests/test_smoke.py`，看哪一行挂就定位哪个模块。

## 10. 最后一条建议

读实验时不要先看“得多少分”，先看四件事：**对照组是什么、随机基线是多少、负例怎么处理、p 值怎么来的**。这四件事决定了一个数字能不能放进研究报告当证据。仓库里的 JSON 和控制台都把这四件事打印出来了，按本文的路径挨个查一遍就能把每个实验讲透。
