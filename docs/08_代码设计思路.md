# 08 代码设计思路（技术方案 × 论文 → 代码的推导）

> **用途**：回答"这段代码为什么这么写"——每个模块从【技术方案要求】+【论文机制】推导出【代码决策】，评审/队友接手时照此阅读。
> **代码位置**：`code/课题3_长短期记忆/memsys/`；方案：`docs/04`；论文依据：`references/` 各笔记。

---

## 0. 总体思路：三层解耦 + 依赖注入

```
┌─────────────────────────────────────────────────┐
│ pipeline.py    七步闭环编排（演示/交付入口）        │  只管"流程顺序"
├─────────────────────────────────────────────────┤
│ controller.py  总调度（SCM：何时写/读/归档）        │  只管"时机决策"
├─────────────────────────────────────────────────┤
│ short_term / long_term / retrieval / evolution   │  只管"各自能力"
│         （四大模块，互不 import 对方）              │
├─────────────────────────────────────────────────┤
│ schema.py      统一数据模型（单一事实源）            │  只管"数据长什么样"
│ llm.py / embeddings.py  外部能力抽象（Mock/真模型）  │  只管"外部依赖"
└─────────────────────────────────────────────────┘
```

**为什么这样分**（对应 docs/04 避坑点）：
1. **检索只读、进化只写**（避坑点 3）→ `long_term/base.py` 把读方法（search/get）与写方法（add/update/remove）分注释成两段，检索层永远摸不到写方法——独立评测不互相污染；
2. **短期与长期边界清晰**（避坑点 2）→ 两把尺子写进类型系统：`WorkingMemorySlot`（场次内）vs `MemoryEntry`（跨场次持久），字段不混用；
3. **可独立消融**（评估节 G0–G5）→ 每个模块可通过 Controller 依赖注入替换/旁路，消融脚本就是"换注入重跑"。

**依赖注入的用意**：`MemoryController(llm=?, embedding=?, factual=?, experiential=?)` 全部可传——Mock（离线/测试）与真模型（BGE/DeepSeek）**业务代码零改动**切换，这正是消融可复现的前提（`docs/04` 第 9 节"可复现配置"）。

## 1. schema.py —— 先定数据，再定行为

**方案要求**（docs/04 1.3 节四类对象）→ **代码决策**：

| 方案对象 | 代码类 | 关键设计决策 | 论文依据 |
|---|---|---|---|
| 短期槽位 | `WorkingMemorySlot` | `working_context` + `fifo_queue` 两字段分离 | MemGPT 分层（working context 常驻 / FIFO 滚动） |
| 长期条目 | `MemoryEntry` | 带 `decay_strength/recall_count/last_recalled_at` 三字段 | MemoryBank 艾宾浩斯所需的 (S, t) 状态 |
| 查询项 | `QueryItem` | 自带 `route` 字段 + `answer_memory_ids` 回填位 | ChatDB Chain-of-Memory（计划显式化）+ MIRIX（路由） |
| 检索结果 | `RetrievedMemory` | 包 `provenance` 而非裸文本 | Zep 双向索引（可溯源=创新点 E） |

**核心方法 `retention()`**：`R = e^(-t/S)` 直接翻译 MemoryBank 公式（笔记_Zhong2023-MemoryBank 第 2.3 节）；`mark_recalled()` 实现"间隔效应"——S+=1 且 t 重置。**为什么放 schema 而不是 evolution**：留存率是"条目自身属性"（随时可查询），遗忘是"进化操作"（批量淘汰）——属性与操作分离，遗忘策略可换而模型不动。

## 2. short_term —— MemGPT 的三机制逐条落地

**论文机制 → 代码映射**（笔记_Packer2023-MemGPT 第 3 节）：

| MemGPT 机制 | 代码位置 | 实现细节 |
|---|---|---|
| 分层存储（main↔external） | `WorkingMemorySlot` vs `controller` 外的长期库 | 槽位只存"当前场次"，长期库独立 |
| memory pressure 预警（70%） | `memory_pressure` property（`used_ratio >= warning_ratio`） | 只读属性，上层据此决定提前归档 |
| flush 递归摘要（100%） | `_flush(keep_ratio=0.5)` | 驱逐最旧 50% → **旧摘要+被驱逐消息 → 新摘要**（递归语义）→ 存 `archived` 不丢 |
| 约束不可压缩 | `compress()` 里"约束字段永不被删"，测试 3 专门断言 | docs/04 避坑点 6 |
| 位置偏置规避 | `render()` 头部放目标/约束，尾部放最新消息 | LongLLMLingua 结论：关键信息放首尾 |

**compression.py 为什么是策略类**：三档（truncate/summarize/llmlingua）对应消融对照组（docs/04 2.1）——`get_strategy(name)` 工厂让 G1 消融一行切换；`LLMLinguaStrategy` 用**延迟导入**（装了包才 import），保证零依赖环境其余功能不受影响。

## 3. long_term —— 为什么是"双库"而不是一个库

**方案要求**（docs/04 2.2：事实记忆+经验记忆两类）→ **决策依据**：

- **事实**要"参数级精确召回"（验收底线）→ 字面/结构化查询强 → **SQLite 行存 + 属性过滤**（ChatDB 符号记忆思想：数据库即记忆，`attrs_json` 列存键值对，`search_attrs()` 是 NL→SQL 的 MVP 形态——真模型后只需加"自然语言→属性条件"解析层，存储不动）；
- **经验**要"语义召回"（同义不同词也能中）→ 向量强 → **内存 dict + 向量索引**（ExpeL 的 Faiss 角色，MVP 用 dict，接口留 FAISS 位）；
- 共同点抽象进 `BaseLongTermStore`（读/写两段接口）→ 未来换存储（如 Zep 图谱替换事实库）只实现接口，上层无感。

**经验库的 `0.8*cosine + 0.2*importance` 加权**：Reflexion 的洞察——失败教训学得最多（`docs/04` 避坑点 5"经验要能改变行为"）；权重写死是 MVP 常数，G3 消融可扫描。

## 4. retrieval —— 查询列表显式化 + 三路融合

**创新点 C 的代码形态**：`QueryItem.route` 由规划阶段决定（"查装备型号"→bm25 字面最稳；"查相似教训"→vector 语义），检索层 `_route()` 按此分发——**检索计划先于检索执行，事后可审计**（`answer_memory_ids` 回填）。

**为什么三路都要**（hybrid.py）：
- vector：同义泛化好，但型号/代号字面反而不稳；
- bm25：字面精确，但"夜间作战教训"查不到"夜袭复盘"（无词重叠）；
- sql：属性精确过滤（装备=T-90），向量永远给不出"参数级"确定性。
- **融合**：归一化（cosine→[0,1]、bm25→max 归一、sql 恒 1）后 `alpha/beta/gamma` 加权——单条记忆多路命中得分累加，天然 RRF 式收益；权重是 G5 消融的扫描点。

**BM25 为什么自己写**（25 行 Okapi）：零依赖优先（老师环境未知），万级语料全量打分够快；换 rank_bm25 时只动 `bm25.py` 一个文件。

## 5. evolution —— 创新点 A 的四操作闭环

**每操作的论文依据与代码决策**：

| 操作 | 论文机制 | 代码决策 |
|---|---|---|
| write | PREMem 链接对：写入前先判"是否已有此知识" | `write()` 全库逐条 cosine > merge_theta(0.80) 判重；**为什么不用 PREMem 的 0.6**：MockEmbedding 分布不同（哈希词袋相似度偏高），注释标明接真模型后回调 0.6 |
| merge | TiM merge / Memp Add⊖Del⊕Update | `merge(ids)` 摘要融合 + **`merged_from` 记录来源**（可回放）+ 删除被合并者 |
| forget | MemoryBank R=e^(-t/S) | `forget()` 批量淘汰 `R < threshold` 且 `importance < 2.0`——**保护线**是关键补充：失败教训（importance≥2）永不遗忘（Reflexion：失败学得最多） |
| abstract | TiM Post-thinking / StructMem 周期整合 | `abstract(ids, theme)` 多条具体经验 → 1 条通用教训，`importance +0.5`（抽象经验更值钱） |

**`evolve_from_review()` 为什么是"复盘驱动入口"**：pipeline ⑦ 只调这一个方法——内部串"抽取→写入（查重）→相邻合并→遗忘→教训抽象"，`EvolutionReport` 把四操作计数返回（消融 G4 直接统计此对象）。**操作建议由 LLM 出**（`llm.extract_memory_ops`，Mem-α 工具化思想），**执行由代码做**——LLM 只建议不落库，保证进化的确定性可回放。

## 6. controller —— 为什么需要"总调度"

**问题**：四大模块互不 import，谁来串？
**答案**：SCM 的 memory controller（笔记_Liang2023-SCM）——"何时写、何时读、读什么"是**时机决策**，不该散在各模块里。

```
start_session()     ① 何时建槽位/装载查询列表
retrieve_and_load() ③④ 何时检索、检索后若 memory_pressure 立即压缩
push()/record()     场次中的信息进出
close_session()     ⑦ 何时触发进化（工作记忆 archived 并入复盘材料——MemGPT flush 不丢）
```

**为什么 controller 是唯一同时碰四模块的角色**：除它之外模块间只通过 schema 数据对象交互——把"耦合"压缩到一个文件内，其余模块保持可独立测试。

## 7. pipeline —— 七步闭环的"编排"与"集成点"

`run_session()` 严格按 docs/04 第 3 节七步顺序编排；两处 `TODO-INTEGRATION` 是**刻意留的集成缝**：
- ⑤ `self.llm.chat(...)` → 换智戎规划管线调用；
- ⑥ Mock 反馈文本 → 换 AFSIM 推演结果 + 评估。

**为什么 Mock 也要写死"部分达成"的反馈**：演示"复盘→教训→下场复用"必须有失败可学——Mock 反馈里预埋了"电子压制"教训，保证 P002 能演示跨场次召回。

**SessionResult 数据结构 = 交付日志格式**：`retrieved`（带溯源）/`plan_output`/`evolution`（四操作计数）/`session_stats`——评估脚本的直接输入，不用二次解析。

## 8. engine.py —— 平台插件为什么用"条件导入"

```python
try:
    from server.engines.memory_plugin_api import EngineCapabilities, MemoryEnginePlugin
except ImportError:
    # 占位基类（形状一致）
```
**原因**：SDK 基类只存在于老师平台服务环境——条件导入让本目录**独立可跑**（冒烟测试不依赖平台），挂进平台时自动用真契约。检索入口把 query 拆成事实/经验两问各打一遍（SDK 单 query 无 target 概念），合并按分排序返回。
