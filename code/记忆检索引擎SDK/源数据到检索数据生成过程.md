# 源数据 → 检索数据生成过程说明

> 本文档说明：把「源数据」逐步加工成「检索数据」、再构建成「向量 + 图谱三元组」的完整过程与各环节职责。
> 对应代码：server/ingest/（构建层）、server/engines/（检索引擎层）、scripts/ingest_all.py（统一入口）。

---

## 一、总体概览：三层加工

系统把知识分成三层，逐层加工，最终让检索引擎能够检索：

```
源数据（原始文件，不经加工）
  │  【构建层】解析 / 抽取 / 结构化
  ▼
检索数据（规范化文件）
  │  【索引层】向量化 / 图谱导入
  ▼
引擎存储（向量 + 图谱）
  │  【检索引擎】查询
  ▼
检索结果
```

| 层 | 位置 | 作用 | 是否自动触发 |
|---|---|---|---|
| 源数据 | data/数据源/、data/Command_KG/ | 原始 PDF / AFSIM / parquet | 手动（待补 watcher） |
| 检索数据 | data/检索数据/ | 构建出的规范化文件 | 手动（构建层产出） |
| 引擎存储 | Qdrant + Neo4j | 向量 + 图谱 | 自动（索引层钩子） |

## 三、数据血缘（四条主线）

### 主线一：条例条令 → 文本 → 向量

```
数据源/条例条令/*.pdf
  ──【build_jmd 文本解析】──→ 检索数据/半结构化数据/doctrine/*.md
  ──【build_kb 向量化】────→ Qdrant knowledge_chunks
  ──【standard_rag】───────→ 检索结果
```

### 主线二：条例条令 → 三元组 → 图 + 向量

```
数据源/条例条令（三元组抽取，离线产出 Command_KG）
  ──【Command_KG parquet】──→ 检索数据/知识图谱数据/*/output/*.parquet
  ──【build_kg 图导入】────→ Neo4j（Entity/Community/CommunityReport/TextUnit + 关系）
                          └→ Qdrant entity_embeddings + relation_embeddings
  ──【graph_rag / light_rag】→ 检索结果
```

### 主线三：AFSIM → 结构化 → 向量 + 图三元组

```
数据源/装备数据库/（AFSIM 模型）
  ──【equipment.db 结构化构建，离线】──→ 检索数据/结构化数据/装备数据库.db
  ──【build_db】──┬─ rag_text 列 ──────→ Qdrant db_text
                 └─ 挂载关系(equipment_mount) → Neo4j :Equipment + :MOUNTS
  ──【struct_rag / graph_rag】→ 检索结果
```

### 主线四：自然语言 → 向量

```
检索数据/自然语言数据/*.txt（红方/蓝方装备描述）
  ──【build_kb 向量化】──→ Qdrant knowledge_chunks
  ──【standard_rag】─────→ 检索结果
```

## 四、四个构建器（server/ingest/builders.py）

| 构建器 | 函数 | 输入 | 输出 | 索引去向 |
|---|---|---|---|---|
| 条令解析器 | build_jmd | 数据源/条例条令/*.pdf | 半结构化数据/doctrine/*.md | 交 build_kb |
| 文本索引器 | build_kb | 检索数据/*.md/*.txt/*.json | Qdrant knowledge_chunks | standard_rag |
| 图谱构建器 | build_kg | 知识图谱数据/*/output/*.parquet | Neo4j + 实体/关系向量 | graph_rag / light_rag |
| 结构化构建器 | build_db | 结构化数据/装备数据库.db | Qdrant db_text + Neo4j 挂载关系 | struct_rag / graph_rag |

## 五、统一清单（增量机制）

清单文件 data/.ingest_manifest.json，按节记录文件级 sha256 指纹：

```
{
  "version": 1,
  "kb":  { "半结构化数据/doctrine/xxx.md": {"sha256": "..."} },
  "jmd": { "JP1_02_110915.md": {"sha256": "..."} },
  "kg":  { "AFDP3_60": {"sha256": "..."} },
  "db":  { "FIGHTER_RCS": {"sha256": "..."} }
}
```

增量判定规则：
- 新增：清单无此键 → 构建
- 修改：sha256 变化 → 重建（先删旧向量再写新）
- 删除：清单有键但磁盘无文件 → 删除对应向量/文件 + 清理清单

## 六、统一入口与触发

- 命令行：python scripts/ingest_all.py --scope kb|jmd|kg|db|all
- 接口：POST /api/v2/memory-engine/reindex  { "scope": "all" }

scope=all 时的执行顺序：jmd → kb → kg → db（jmd 先产出 .md，kb 才能向量化）。

## 七、索引层（检索数据 → 向量+图）

检索数据文件变更 → notify_data_changed(rel_path, action) → 按扩展名认领插件 → 按粒度路由：
- 文件级（.md/.txt/.json）→ ingest_file → Qdrant 向量
- 目录级（.parquet KG）→ ingest_directory → Neo4j + 实体/关系向量

说明：前端文件管理 CRUD 已接入此钩子；构建层产出检索数据文件后也走此入口（目前由 ingest_all.py 顺序触发，源数据 watcher 待补）。

## 八、检索引擎（向量+图 → 检索结果）

| 引擎 | 后端 | 检索内容 |
|---|---|---|
| standard_rag | Qdrant knowledge_chunks | 文本语义 |
| graph_rag | Neo4j + entity_embeddings | 图谱 + 实体向量 |
| light_rag | 共享底座（Neo4j + Qdrant） | 混合检索 |
| struct_rag | 复用 standard_rag 的 Qdrant | 结构化数据 |
| plan_rag | Agent 编排（委托其他引擎） | 历史方案 |

## 九、完整链路示例：新增一个条例条令 PDF

1. 把「JP 3-99 某条令.pdf」放进 data/数据源/条例条令/
2. 执行 python scripts/ingest_all.py --scope jmd（或 --scope all）：
   - build_jmd 检测到新 PDF（sha256 不在清单）→ 解析 → 写 半结构化数据/doctrine/JP 3-99 某条令.md
   - 清单 jmd 节记下该 PDF 指纹
3. build_kb 检测到新 .md → 分块 → 向量化 → Qdrant knowledge_chunks
4. standard_rag 即可检索到该条令内容

图数据线：新增 Command_KG parquet → build_kg → Neo4j + 实体/关系向量。
结构化线：AFSIM 变更 → build_db → rag_text 向量 + 挂载关系三元组。
